## Concrete broken boundaries

**1. Live evidence can enter the ordinary enrollment DAG and become ineligible for verification.** `_replica-liveness.js:413` queues ordinary `integrity`. `_replica-processing/queue.js:38` admits quarantined/processing sources without distinguishing capture purpose. `_replica-processing/runtime.js:265` is actually called by both the API sweep (`sweep.js:85`) and native worker ([services/replica-processing-worker/run-once.js:156](C:/Users/raghav.s/Desktop/build/Vyakti-platform/scratchpad/expert-integration/services/replica-processing-worker/run-once.js:156)). The worker validates ownership and state but not capture mode (`worker.js:467`; `contracts.js:112`). Its successful integrity result schedules malware, and malware schedules media-probe, then diarization, separation, enhancement, transcription and voice quality (`pipeline.js:6`, `:17`; `worker.js:528`).

The commit changes every non-final successful source to `processing`, then `ready` after voice quality (`repository.js:216`). Liveness leasing and settlement require `quarantined` (`_replica-liveness-verification.js:200`, `:351`). Thus an ordinary integrity completion can strand an uploaded challenge before composite verification, or invalidate an already leased attempt. Even where later adapters are unavailable, the first successful integrity state change is sufficient. With available adapters, narrowly consented verification media can reach enrollment transformations. No capture-mode exclusion was found in the actual worker, storage-writer admission, source contract or commit. This is source-proven control flow; it was not executed in this audit.

**2. The configured composite service operation does not exist.** `_liveness/providers/azure-composite.js:17` requires `/v1/liveness/verify`; its `verify` implementation signs media/ID URLs and expects recognized speech, continuity/risk scores, single-speaker/capture binding and acceptance. [services/azure-verifier/src/server.js:19](C:/Users/raghav.s/Desktop/build/Vyakti-platform/scratchpad/expert-integration/services/azure-verifier/src/server.js:19) registers identity and Face session/resume/result/delete/cleanup, but not that operation. A request to the supplied route table receives 404. Adding only a route is insufficient: middleware requires `broker_nonce` and `broker_issued_at` (`server.js:60`), omitted by this adapter's payload (`azure-composite.js:95`).

`createLivenessVerdict` uses policy `vyakti-liveness-composite/v2`, combining separate official Face proof with phrase similarity, continuity, synthetic risk and binding (`_replica-liveness-verification.js:106`). Its raw Face score fields are not the official authority. No measured producer for the missing continuity/risk/binding claims was found. Threshold constants are not calibration. The detached `identity_audio`/speech-v2 primitives do not implement this operation or its policy.

**3. Two distinct continuity gaps remain.** Face compares the person in the provider session to the document. That session is deleted **before** the later phrase video is recorded. A shared owner/challenge ID and time window do not establish that the later visible person is the same document subject, that their lips produced the audio, or that replay/injection was resisted. A server-derived audio track can establish byte ancestry but not those human facts.

Separately, the lease carries challenge video and ID descriptors plus Face proof (`_replica-liveness-verification.js:251`), but no primary enrollment source, selected window or reference embedding. Settlement does not compare the earlier enrollment voice to the verified subject. Downstream review requires two embedding families, owner-approved measurements and selected audio (`_replica-review.js:103`; `_replica-processing/builders.js:71`), but that is not a measured challenge-to-enrollment speaker match. These are independent obligations; repairing one does not establish the other.

**4. Document review is still an external prerequisite.** [services/azure-verifier/src/review.js:7](C:/Users/raghav.s/Desktop/build/Vyakti-platform/scratchpad/expert-integration/services/azure-verifier/src/review.js:7) is an outbound client for `/v1/document/review`, with signed exact-document/version responses and explicit pending refusal. The inspected service has no implementing route. The prior cross-ref audit found only clients/tests, not a deployed review authority. Document Intelligence extraction and a portrait do not substitute for authenticity review. This can block the modern journey before Face starts.

## Consent and concurrent mutation limits

Existing protections are substantial: issuance checks active capture/storage; source creation stores the selected capture consent ID; Face and composite stages require the challenge-specific active biometric verification grant; completion binds lease, provider version, input SHA, current authentic adult ID and quarantined sources. Cancellation and capture/storage/biometric withdrawal explicitly revoke cases/grants, fail challenges, clear leases, queue source erasure and clear replica identity stamps (`_replica-consent.js:300`). A completed withdrawal is not equivalent to an active grant.

Do not infer concurrent safety from those sequential predicates. Modern finalization (`_replica-liveness.js:379`) has no replica/consent row join or authority locks, and its dependent source/challenge updates do not repeat the original pending/issued predicates. Lease and settlement lock the challenge, while other source, identity and consent rows are snapshot reads; the final replica mutation repeats age but not all lifecycle/policy authority (`_replica-liveness-verification.js:334`, `:389`). Exact source-bound capture consent is not revalidated there. The revocation cascade mitigates ordinary completed withdrawal, but overlapping cancellation, source deletion, replacement grants, natural expiry and settlement need real transaction witnesses before claiming no revival or partial state. These are concrete missing guards/race candidates, not a claimed executed exploit.

## Smallest next repair: preserve a verification intake quarantine

Do **not** simply delete the integrity job or treat missing scans as clean. No new scanner service is necessary for the bounded intake correction: existing `providers/native-media.js:37` verifies actual private bytes, and `:50` invokes native ClamAV. `native-tools.js:169` accepts only the actual clean exit/output pair; infection is false and scanner failure throws. `composition.js:160` wires these adapters and omits unavailable native capabilities. A serverless runtime's missing scanner is an explicit blocked prerequisite; a native worker with current signatures and the exact development DB/storage configuration must be verified separately.

A minimal complete patch should:

1. Give `capture_mode=live_challenge` a purpose-specific intake DAG: integrity → malware_scan → stop. Keep the same owned immutable original and existing durable jobs/attempts. Successful steps retain `quarantined`; produce no enrollment artifact, transcript, embedding or normal voice build. Ordinary uploads keep their current DAG and ready-state semantics.
2. Enforce that purpose/step rule at queue admission, actual worker execution and atomic commit, including stale already-leased jobs. Reject historical media-probe-and-later live jobs before provider/storage effects, and prevent their old outputs from committing. A planner-only branch leaves pre-existing queued work unsafe.
3. Require successful integrity and malware receipts for the **exact current source SHA, owner/replica, job revision and completed attempt** at both liveness lease and settlement, with real adapter provenance and matching receipt commitments. Current liveness lease checks neither job, so merely preserving quarantine would allow verification to race ahead of scanning. Unavailable, infected, hash-mismatched or uncertain scans must never authorize a verifier call.
4. Reuse source/grant authority checks for both preflight and settlement; coordinate with cancellation/deletion/withdrawal locks. Do not relax source-state predicates to accept ordinary `processing`/`ready`. Any historical derived artifacts need separately authorized exact-source cleanup, not automatic promotion back to quarantine.

Expected files: `_replica-processing/pipeline.js`, `worker.js`, `queue.js`, `runtime.js`, `repository.js`, and `_replica-liveness-verification.js`; inspect storage-writer admission if a stale lease could reach effects before the new execution guard. `_replica-liveness.js` may retain the initial integrity enqueue. Dedicated focused evals and an opt-in SQL harness should accompany the patch. Existing receipt/job schema appears sufficient for intake; confirm exact receipt fields and real SQL before deciding no migration is necessary. This slice makes intake honest, **not identity acceptance available**. Leave the missing composite and every identity grant-writing policy disabled/unmodified until separately accepted.

Proof required: actual-function clean/infected/unavailable/hash mismatch controls; both ordinary and live modes; prequeued and preleased forbidden stages; zero provider/artifact calls on refusal; real SQL execution and original-DAG negative control demonstrating the quarantine escape; two-transaction scan/verification ordering and cancellation/withdrawal/deletion overlaps; exact manifest and all-table cleanup. EXPLAIN is additional parser evidence, not execution proof. Then an authorized native scanner run must establish actual capability without invoking face/voice models.

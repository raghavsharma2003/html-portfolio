# Expert value contract

7 September 2026. Proposed acceptance contract for `codex/expert-unified`; source inspection only. This document adds no runtime, evaluation or deployment result. The parent task owns the pending complete release run and context log.

## The first useful outcome

A learner in an expert's existing paid cohort brings a failed practice attempt between human sessions. The expert's AI identifies the failed step using the expert's approved material, explains it in the expert's accepted teaching style, and produces one appropriate next exercise. At the next visit it checks that learner's progress. When it cannot resolve the issue, the learner can share an exact, reviewed question with the human expert and receive their answer.

This is a proposed paid outcome: a completed learning step and less repeated expert work. A familiar voice, a long conversation, message counts and an upgrade prompt do not establish that outcome. No willingness-to-pay, renewal, learning gain or expert time saving is claimed. Start with one willing Hindi/Hinglish educator and one topic; broaden only after the complete task works. The broader pilot proposal remains in [the research brief](report-source.md).

## Five observable acceptance scenarios

These are proposed requirements, not passing tests. Preserve exact source, decision, profile, answer and action identifiers for each run. Use real authenticated development routes and current database predicates; mocks alone cannot establish any lifecycle below.

| Scenario | Observable completion and negative control |
|---|---|
| 1. Ground a learning step | Feed one owner-approved lesson and worked example. A client submits a related failed attempt; the answer identifies the error and cites the actual eligible source/span. A question absent from the corpus produces an honest unknown or requests clarification. A revoked/unapproved source cannot support a later answer. Test Hindi, Roman Hinglish and English separately, including a Roman query with Devanagari evidence. |
| 2. Transfer an owner correction | Save a written correction to one answer; show its receipt and pending state. Before approval, ordinary behavior is unchanged. After explicit approval and the required published-version update, the original case and an unseen related case follow the correction; an unrelated case retains its accepted behavior. The owner judges explanation order, uncertainty and interpersonal style against their own rubric. Rejection/undo removes subsequent influence without erasing decision history. |
| 3. Continue privately | Client A returns in a new session after more than eight unrelated recent facts and is asked about their actual earlier failed step and commitment. Client B and another expert receive none of A's details. A memory-off client creates no persistent episode/fact history. Forget/retraction removes the corresponding recall and derived task context; a pending erasure receipt is shown as pending. |
| 4. Complete one delegated skill | The owner enables only “review this practice attempt and propose one next exercise,” with approved examples, permitted inputs and a clear success rubric. Its result is a structured, inspectable task artifact tied to the client and source version; the expert persona explains the result through the existing reply gate. A deterministic answer key or named checker validates the exercise where applicable. Saving a follow-up uses explicit client opt-in through the existing check-in mechanism. Repeated submission has one effect and a recoverable receipt; failure cannot be rendered as completion. Requests to send a message, post socially or invoke another tool remain outside this skill. This artifact/executor connection is new work. |
| 5. Owner override and human resolution | An unresolved question offers the existing handoff. The client selects and sees precisely what the owner would receive; no other private history appears. In an authorized acceptance run, explicit send creates one request, the owner answers, and only that client receives it. Withdrawing before answer prevents a later answer; disabling the action, pausing the Room or revoking applicable authority prevents new effects. “Never say this” remains enforced on client replies and check-ins. No outbound operation is performed by this audit. |

All five require model calls to remain on Azure/Foundry or the owner's Azure-hosted model services, including retrieval embeddings, extraction, ASR, reply, evaluation and voice. This is an acceptance constraint, not current global enforcement. [_surface.think](../../../../api/_surface.js) chooses Azure only with `VYAKTI_REPLY_PROVIDER=azure_foundry` and otherwise retains an OpenRouter path; [claim extraction](../../../../api/_claim-extraction/registry.js) also retains an OpenRouter fallback. Inventory every active model caller, prohibit non-Azure fallback and retain endpoint/model receipts before the integrated trial. Storage/auth/payment services are separate from model serving.

Voice acceptance remains independent: complete real enrollment and protected playback, then run the [listening methodology](voice-listening-methodology.md). A source citation or successfully executed skill does not establish the owner's voice likeness, delivery or listening quality.

## Smallest next vertical and expansion boundary

Implement the single practice task inside the existing Feed, Meet, Deploy and Rooms journey. First close the approved expert-source-to-Room-answer path with citations and abstention, then carry one approved correction into that same client path. Add only the typed practice artifact and bounded executor needed by scenario 4; reuse current identity, review, memory, handoff and check-in authorities. Keep expert style as a reviewed persona version around execution, not as instructions that grant tool authority. The task result must expose evidence and status before the persona explains it.

For a first pilot, record a baseline week of the expert's repeated questions and review minutes, then record resolved tasks, learner completion, reviewed expert minutes saved, repeat use, support burden and renewal. These measurements would test value; existing turn counters and `sessionWorked` heuristics do not substitute for them. Reverse this vertical choice if observed client tasks or expert interviews show a different recurring job with clearer completion and less review burden.

Later personal representation may reuse the same identity and review mechanisms, but each new audience needs its own disclosure and memory boundary. Social posting needs platform-specific authority, an exact content preview, owner approval, expiry/revocation, idempotency and delivery receipts. Agent-to-agent work additionally needs recipient identity, a bounded purpose, allowed inputs/outputs, current grant checks and cancellation before effects. Human handoff is a reusable pattern, not proof these capabilities exist. No skill, new audience or approval may silently publish private client history or rewrite the expert's personality.

Evidence boundary: this audit inspected callers on 7 September 2026 and ran `node scripts/context.mjs --check` successfully (2,036 nodes, 2,345 edges). It ran no model, upload, skill, handoff, publication, browser or paid-pilot test and did not change runtime code or context files.

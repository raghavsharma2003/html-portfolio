# Correction worker source review

Date: 2026-09-08. Method: source inspection only of the new worker, artifact renderer, HTTP handler and migration 152, plus their existing runtime, feedback, candidate and budget dependencies. No tests, SQL, network, model calls or Node execution. These findings describe the inspected initial source; subsequent parent fixes need their own verification.

## Findings

1. **High: durable dispatch admission does not enforce current authority.** `basis()` reloads active runtime consent, identity and a reconstructed feedback set. The subsequent update that changes the job to `running` only predicates dataset ownership, draft status and saved source hash. Revoking inference consent, retiring/superseding the runtime, or changing feedback between these statements does not prevent dispatch of the already-read private pairs. Dataset `source_set_hash` is an immutable saved snapshot, not a recomputation of current feedback. Put active authority and expected current feedback comparison in the atomic admission operation, using the existing source/version fields and locking conventions. Test a mutation after the last application-level read and before admission; it must result in zero provider calls.

2. **High: measured usage is lost on a semantically rejected proposal.** `validateCorrectionStrategyProposal` runs before the response/usage receipt and before `settleFoundrySpend`. A valid Azure response with measured usage but unsupported strategy IDs or insufficient supporting sessions throws here. The catch marks the operation unknown, stores no measured usage, and holds the entire reservation even though the call outcome and token usage are known. Persist measured response identity/usage before semantic validation and settle that usage regardless of proposal acceptance. Record the semantic refusal as a failed proposal separately. Preserve debt only where settlement is actually ambiguous. Test an invalid proposal accompanied by valid usage and a second request that cannot dispatch again.

3. **High: final candidate registration can race baseline retirement.** The final `basis()` check precedes artifact save and `registerOwnedCandidate`. That existing registration helper deliberately accepts capability states `active` and `superseded`. The new job completion statement checks a draft dataset and candidate hashes but not current runtime authority or current source evidence. A baseline superseded after the read can therefore yield a draft receipt. Bind final materialization/registration to the original current capability and source fingerprint in SQL, or keep the result in a clearly stale held state. No runtime activation currently occurs, which limits the impact but does not establish current candidate eligibility.

4. **Medium: idempotent conflict returns an unrelated latest job.** The insertion conflict key is `(dataset_id, model_commitment, protocol)`, while `readOwnedCorrectionCandidate` fetches the latest job for the dataset without the commitment/protocol. If model A already has a job and model B subsequently created a newer job, a repeat request for A returns B's job. Fetch the exact conflict row (or exact original job ID) for the worker result. Keep a separate latest-job UI read if desired. A two-model, same-dataset fixture should demonstrate this.

5. **Medium: migration does not bind candidate to job dataset.** The candidate FK is `(candidate_id, replica_id, owner_user_id)`, permitting a same-owner candidate from a different dataset to be linked to the job. The completion update also omits `c.dataset_id=j.dataset_id`. Migration 032 already supplies a unique index for `(candidate_id,dataset_id,replica_id,owner_user_id)`. Use that composite relationship and the matching SQL predicate so fixture mistakes and future writers cannot cross-wire candidate provenance.

6. **Remaining product gap: artifact is stored, but no evaluation materializer consumes it.** The pure renderer compiles a private experimental core and truthfully labels it unapproved. The worker persists the policy artifact and registers its hash, but the renderer comment itself identifies the blind materializer as future work. This is real artifact preparation, not end-to-end candidate comparison or owner approval. A later materializer must load the exact stored artifact, verify its hash/build manifest/current authority, render the held candidate, and bind generated outputs to existing blind assignments without changing the active persona.

## Positive source observations and limits

- New SQL parameter positions match their supplied argument counts by manual inspection; UUID comparisons in the new statements are explicitly cast. This is not a PostgreSQL parse/type-check claim.
- Migration 030 supplies the three-column dataset identity unique constraint; migration 031 supplies the three-column candidate identity unique constraint. The initial migration's declared FKs therefore have visible source targets, subject to real database verification.
- The provider start path has a durable unique job and conditional preparing-to-running transition. Repeat calls cannot blindly dispatch that job again. An exception after `beginFoundrySpend` but before `providerStarted=true` is known to be pre-dispatch; release is allowed by the existing ledger implementation. A crash in this interval may retain funds, but does not justify automatic replay.
- Exceptions after dispatch retain debt rather than release it. Settlement failures retain response/usage receipts only when semantic validation already succeeded, which is the accounting defect above.
- Artifact rendering removes approved calibration entries for changed axes and labels replacement shapes experimental. It does not write active profile/calibration or fabricate owner approval.
- The job's dataset deletion cascade handles dataset/owner erasure. Whether source deletion also invalidates or erases every derived saved artifact requires the complete erasure path and real SQL tests; these new FKs alone do not establish that guarantee.

## Resolution review before source freeze

Re-inspected the revised source on 2026-09-08. No additional blocking source defect was identified for the explicitly held private-draft preparation slice. This is not release approval or a claim that candidate learning works end to end.

- Findings 1 and 3 have source fixes: the exact exported `OWNED_RUNTIME_CONTEXT_SQL` is reused by the ordinary runtime loader and the new current-authority CTE. The CTE also compares the full current feedback and split-assignment arrays to the read snapshot. It gates job admission, final pre-dispatch read, artifact save, candidate registration and completion. Registration's optional fourth argument is populated by fixed server-owned SQL, not HTTP data; its placeholders shift by 10 and its values follow the original 10 registration arguments. Real PostgreSQL parsing, row types, concurrent revocation and source-erasure behavior remain unproved here.
- Finding 2 has a source fix: semantic validation captures its error; valid measured usage is persisted and settled before that error is raised. The worker fixture executed this path and observed a failed proposal with settled usage and no repeated dispatch.
- Finding 4 is fixed on the conflict/replay path: the exact dataset/model/protocol row is selected. The successful and abstained paths still use the latest-dataset reader. Under concurrent different-model jobs, that can return another job's receipt. This is a remaining receipt-correlation issue rather than authority to dispatch or activate another candidate; use exact current-job reads for those terminal responses when closing it.
- Finding 5 has a source fix: migration 152 now uses `(candidate_id,dataset_id,replica_id,owner_user_id)` and completion checks candidate dataset equality.
- Finding 6 remains intentionally open. A private policy artifact can be rendered, but the blind evaluation materializer is not implemented or claimed by this slice.

The focused worker suite ran after the reservation was lifted: `node evals/correction-candidate-worker/run.mjs`, Node 24.13.0, terminal exit 0, seven groups. It executes actual worker, crypto, dataset preparation, token meter, artifact renderer and registration against a stateful SQL fixture. Every provider fixture checks that only 32 training preference examples enter the request and that holdout plaintext is absent. First execution failed before tests because ignored `_config.js` was missing; the parent provisioned a verified inert config before the successful run. No real database or Azure calls were made.

Additional limits: an identical policy from another model has the same artifact hash but a different build manifest; the existing candidate registry may refuse that duplicate hypothesis instead of registering it again. A crashed or ambiguous job deliberately cannot replay automatically, and operator reconciliation remains necessary. The parent reports a 20-shape SQL inventory prepared for the separate database proof; this final source review did not execute that inventory or treat its existence as parser evidence.

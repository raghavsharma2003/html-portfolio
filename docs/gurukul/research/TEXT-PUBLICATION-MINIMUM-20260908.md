## Complete vertical slice

**Scope proposed for the first link:** one existing owner-authored canonical source, one explicitly reviewed public teaching projection, physics/chemistry/maths, web text, signed-in visitors, no persistent relational memory or source-file download. Apply existing mentor/child-safety output constraints to everyone. Reuse existing age-attestation semantics only for an explicitly adult audience; do not describe self-attestation as verified age. Supporting actual minors requires the corresponding agreed audience/guardian contract, not simply omitting admission.

1. **Owner review and publish.** Add a focused panel at the existing `src/studio/ExpertSharePanel.tsx` entry, also reachable from the ordinary personal `CloneExperience.tsx`. Reuse source choices and safe draft projection, not an automatic full private-sheet copy. Server GET returns exact source title, published fields, disclosure, audience, term, quota and a review commitment. A separate explicit POST with those commitments and versioned statements atomically creates the publication and its genuine account-text permission. No model call occurs on review/publish/navigation. Lost-response replay returns the same publication; changed source/projection/terms require new review. Add owner get/status/unpublish/replace and actual controls in this same slice.
2. **Public landing and visitor admission.** Use one clone share destination, with its early-text resolver while no verified runtime exists, rather than manufacturing a Room that cannot resolve without `vy_agent`. Keep it attached to the same replica/public identifier for later permitted lanes. Show the AI/material-account provenance in app UI before any answer and on identity questions. Authenticate the visitor separately; bind visitor, publication/version, disclosure digest, audience receipt and expiration in a server-issued session. Restrict all subsequent result reads to that visitor. A public URL is discovery, not permission to read private owner material or another visitor's questions.
3. **Actual question and reply.** Add a text-only endpoint with `open`, `join`, `ask`, `result` and `forget` operations. Validate current publication/source/permission, reserve visitor quota, admit one durable request ID, reserve the existing Azure token budget, exclusively claim dispatch, call the existing structured Azure adapter once, settle actual usage, run shared output/never-rule gates, then revalidate current authority before storing/delivering. Same-ID replay reads the stored result; changed-payload replay rejects. Uncertain billing remains uncertain and blocks blind retry. State clearly whether a failed admitted request counts toward the allowance; provider costs remain payable even when delivery is withheld.
4. **Usable withdrawal and cleanup.** Unpublish stops new admission and withholds in-flight/previous results under revoked authority. Source removal, source/account permission withdrawal and replica erasure perform the equivalent structural invalidation and dispose of every copied projection/question/answer payload. Visitor forget deletes that visitor's payloads without erasing publisher material or another visitor. Never reuse revoked public identifiers. Retain content-free settled spend/audit evidence independently from deleted content.

## Authorized implementation and explicit operating terms

The user wants a full clone, and early text publication should advance that exact journey. The implementation can proceed under a truthful limited-capability disclosure: answers come from AI using this account's reviewed published material; current real-world identity/voice has not been verified. Existing teacher-clone policy supports separate text consent but cannot supply absent principal verification. Do not imply owner reading/relay or verified first-person credentials. This disclosure/capability distinction is required implementation behavior, not an invitation to substitute a different product.

Audience, term and retention must be displayed in the review and final receipt; quota/spend ceilings must be explicit bounded deployment configuration. An adult signed-in pilot is a restrictive implementation proposal, not permission to serve minors or incur uncapped costs. The code and synthetic end-to-end proof can proceed with explicit fixture values; deployment or a paid proof uses the separately authorized actual budget and audience. The new per-publication grant requires no policy clarification merely because it is new: implement its review and final user tap now, and obtain the actual grant through that product interaction. No new paid inference or public access occurred in this audit.

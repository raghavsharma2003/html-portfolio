# One useful next voice step

8 September 2026. Read-only research and source audit for the Vyakti owner. Scope: Azure/Foundry inference or Azure-hosted weights, no local Docker, no continuous GPU floor, and real Hindi/Hinglish/English speaker likeness. This report alone was written. No model generation, listening, owner media access, database/cloud request, build, installation, deployment or spending occurred. Source inspection used ROOT/context/STATE.md and the current ROOT/scratchpad/expert-25-combined tree (STAGING below). It does not freeze or accept that actively integrated tree.

## Decision

**There is no defensible ordinary-owner likeness experiment to execute now without resolving external identity evidence and owner evaluation prerequisites. The highest-value bounded preparation is a versioned recorded-pack adapter for the existing protected listening harness.** It should accept a frozen corpus and explicit comparison-reference manifest, retain failures and exact provenance, and prove that only genuinely matched owner/text/conditioning cells can be compared. This is an engineering prerequisite, not a claim that building a harness improves the voice.

Do not start another model sweep. The September 7 frontier report already identifies a reasonable first comparison: existing Chatterbox Multilingual as the common baseline, existing IndicF5 in Hindi and experimental chemistry Hinglish, existing Qwen3-TTS Base in English only. The missing result is a controlled, protected, blind owner/native-listener comparison; a newer model card cannot supply it. The adapter lets that comparison be prepared without accessing owner audio or granting identity, and avoids reopening the safety contract simply to hear a sample.

## Bounded implementation prerequisite, ready to commission

Add one new, explicit recorded-pack mode to the existing benchmark; leave historic loaders/contracts intact. Do not disguise a new run as an August pack or relax its counts. The new run manifest must bind:

1. Corpus version/hash and preregistered item IDs, eligible language cells, candidate identities and attempt count. Every attempted generation has one terminal success/failure/uncertain record; failed clips remain in denominators and produce no fabricated audio.
2. Opaque subject ID; authorized enrollment/conditioning reference manifest and independent listening-reference manifest as separate purposes; hashes for audio/transcript, reference preprocessing, model/tokenizer/vocoder/adapter or explicit `none`, runtime image and settings. Source authority is a verified external input, never a boolean created by the benchmark. Preparation mode may use clearly synthetic fixtures but must not mark them as real protected speaker evidence.
3. Original text, normalized synthesis text and reconstruction receipt, output hash, generation ID, disclosure/protection receipt, delivery transformation history and cost/timing record. Do not expose private mappings, media locators, authority tokens or owner identity in the served tree.
4. Comparison key includes speaker, language, exact source text and a declared matched-conditioning group. Candidate may vary inside that group. Different references, preprocessing or normalization can form a declared pipeline comparison, but must not masquerade as a weights-only effect. Different speakers cannot share one owner-reference player.

The corpus count is manifest-derived. Success and failure counts must reconcile against the preregistered attempts; unsupported lanes are excluded before generation. Reuse the existing four 1–5 ratings (`owner_likeness`, `naturalness`, `indian_accent`, `pronunciation`). The proposed A/B/tie/cannot-judge, meaning and prosody judgments require an explicitly versioned supplement; they are not existing UI fields. Preparation can validate bindings and seal empty run plans without any media, network, inference or grants.

Meaningful acceptance controls: execute existing-loader compatibility; a new-pack successful fixture and exact recorded-pack re-verification; reject substituted output/reference/text/receipt/corpus hash, duplicate/missing attempts and unknown candidates; prevent same-text different-owner/reference cells from merging; keep failures visible without playable clips; prove served output cannot reveal private mappings; retain honest `not_started`/`not_rated` states. Prove any common padding/loudness transformation retains its original bytes/receipt relationship and required protection. Offline fixtures prove these mechanics only. No SQL schema or production voice routing change is part of this prerequisite.

### Exact isolated implementation acceptance plan

Suggested boundary: one new pure loader/validator module under `evals/voice-listening-benchmark/`, a new explicit mode in `scripts/voice-listening-benchmark.mjs`, scoped cell support in the existing library, focused portable tests and context entries. Do not modify runtime providers, identity intake, voice activation, GPU configuration or historical pack schemas. No synthesis/import side effect, network client or automatic historical owner-media read belongs in the new mode.

* **Explicit run contract.** New contract such as `vyakti-recorded-listening-pack/v1` carries `runId`, `runPlanSha256`, `corpusId`/hash and its candidate/attempt inventory. A same-file duplicate run ID or attempt ID rejects; cross-run entries reject even when their text/audio is byte-identical. `prepare` validates/seals a no-media plan and stays `not_started`; `build` requires the complete declared outcome inventory. Partial fixture preparation cannot become a real listening pack by toggling a boolean. The historic CLI remains the default and rejects mixed legacy/new flags.
* **Scoped grouping before text.** New-path comparison scope is `(runId, subjectId, conditioningGroupId, listeningReferenceManifestSha256, comparisonRecipeId)` followed by `(language, exactSourceTextSha256)`. Scope fields are mandatory for the new contract and cannot default to a historic owner. Candidate identity stays outside the key so the intended arms can compare; recipe identity commits the declared arm-specific normalization policy rather than accidentally separating every candidate. Each conditioning group explicitly maps each candidate to its exact reference/transcript/preprocessing hash. A knowingly unequal reference recipe is labeled a pipeline comparison. Historic single-owner grouping stays compatible, without accepting missing new scope via that branch.
* **Reference selection.** For each trial, the served reference player resolves through the same scoped subject/listening-reference mapping. A reference cannot be borrowed from another subject because the bytes happen to exist. If extending the current single-reference UI is out of this slice, explicitly restrict each new run to one subject and one listening-reference manifest, while still rejecting cross-subject/reference cells in the pure validator. Do not silently serve the first reference. Multiple runs can cover multiple speakers later.
* **Portable executed negatives.** Commit an exact-byte snapshot of the bounded old loader/grouping functions with SHA-256 in a test fixture. Execute it to reproduce unknown-new-pack refusal and same-language/text cross-subject merging. Do not require the isolated branch, worktree paths or a parent-only Git object. New tests execute actual exported functions, not an independently reimplemented algorithm or source regex. Generated fixture WAVs may be tones and explicitly synthetic receipt fixtures, never a real protected voice proof.
* **Provenance/refusal matrix.** At minimum execute independent mutations for run/corpus/text/reference/receipt/output substitutions, changed candidate/reference mapping, duplicate/missing attempt, foreign subject, foreign run, same source text with different conditioning group, different text in the same scope, mismatched normalized-text receipt, protected-status boolean without required evidence and escaped/out-of-root media path. Unknown signature/key/authority verification must stay unverified; implement against existing verifiers when available, otherwise block real-media build rather than inventing accepted evidence. Valid fixtures demonstrate mechanics through an explicit test-only verifier, impossible to select from the real CLI.
* **Failure and exposure matrix.** One failed and one uncertain attempt remain in the plan/result denominator without waveform or successful rating row. No pairwise winner from a lone successful arm. Public serialization omits names, engine mapping, private source path, reference authority material and signing data. Opaque IDs remain stable within the sealed run but do not join separate runs. Re-verification reads every source/output commitment back and rejects drift. Existing protection-aware common audio treatment stays common and auditable; reject a clip if preservation/verification of required protection cannot be established.
* **Completion evidence.** Run focused new loader/scoping tests plus existing listening-library/schema tests with network/provider calls hard-failed and counted zero. Use a temporary test directory with portable fixture files; never consume historical private owner packs just to make a regression test pass. If the CLI/public UI changes, verify the resulting synthetic pack and actual reference-selection behavior with a bounded loopback test, separately labeled from human listening. Provide exact changed-file hashes, retained old-negative fixture hashes, test counts/output and a truthful missing-external-evidence list. Root owns the integrated release gate; the isolate does not start a second full release while combined25 runs.

These are implementation acceptance criteria, not tests executed during this report. This slice ends with an instrument that can prepare and validate a correctly scoped experiment; it ends with **zero generations and zero owner-quality judgments**.

## One later experiment, after prerequisites

Use the existing September 7 **matched protected pipeline feasibility comparison** rather than design a second leaderboard. Baseline: frozen general Chatterbox V3 in every lane. Candidate: pinned IndicF5 (`ba85abedf18dc479a447eaa0eccbd76ab78a47d5`) in Hindi and chemistry Hinglish; pinned Qwen Base in Indian English. No fine-tuning arm and no model/provider fallback. A small preregistered first-owner run could use four independent utterances per lane, two pipelines each, **24 total held-out dispatch attempts** with no retries/best-of selection. This is a proposed feasibility cap, not approved spend or a power calculation. It cannot establish population superiority. A broader 72-attempt/three-speaker plan already exists and should follow only if useful, not automatically.

The authored corpus currently has 60 unique prompts, 20 each `hi`, `hi-Latn`, `en-IN` (counted today). It is **candidate holdout**, not established independent data, and many prompts are outside chemistry. Choose eligible chemistry utterances under the existing IndicF5 contract on a language/domain audit before any render; if insufficient, author replacements under a new corpus version. Do not widen the runtime contract to make the corpus fit. Audit overlap against enrollment, fine-tuning, development and correction material; separate reviewed comparison recordings from conditioning recordings. Record every normalization and keep identical source text between arms in each lane. Preserve continuous Hinglish utterances and separately score switch boundaries, names, units, numerals, negation and uncertainty.

Owner and at least five authorized bilingual listeners rate identity/naturalness/accent/pronunciation separately, with recorded familiarity and access to independent owner speech. Supplemental judgments mark critical meaning errors and prosody problems with spans, A/B/tie/cannot-judge and both-unacceptable options. The owner must personally accept likeness; unfamiliar listeners without comparison material cannot provide that result. Keep Hindi/Hinglish/English separate. ECAPA/ASR may diagnose failures but cannot become a fidelity percentage or replace listening. Four utterances per lane support descriptive feasibility findings, not credible narrow confidence bounds or stable p95 estimates.

Measure timestamps for request, admission, runtime ready, synthesis start/end, provider-protected complete, app seal and first browser-playable **protected** audio. Report the full observed cold/warm sequences with n, failures, timeouts and unknown states. Warmth must use actual runtime evidence, not elapsed time assumptions. Pre-register ordering/cold-state policy; any separately authorized commissioning/warm-up requests count against spend even when their audio is discarded. Preserve `minReplicas=0`, use bounded existing Azure services, and observe actual return to zero without repeatedly waking them. Cost is total incremental GPU/vCPU/GiB allocated seconds plus broker/protection/storage/request/egress meters, with dated regional rates and usage/invoice reconciliation; distinguish estimate, reconciled spend and unresolved allocation. Include startup/cooldown and failed attempts. No unit-price estimate is substituted for actual usage.

Stop before generation if source authority, independent comparison reference, immutable runtime identity, compatible protection receipt, corpus independence, explicit cost/time/attempt cap or compatible modern identity evidence is missing. Stop dispatch on protection/binding failure or exhausted/uncertain budget; reconcile in-flight work without retrying it blindly. Stop adoption if owner likeness is rejected, critical meaning changes occur or any lane regresses beyond owner-approved limits. Fix commissioning issues on separate material and freeze again before opening an untouched holdout. Do not tune on failed held-out items and rerun them as new acceptance evidence.

**External prerequisites remain:** versioned modern issued/source-ownership contract; calibrated composite visual/speaker/anti-spoof producer and compatible revisions; real subscription/provider entitlement evidence; exact source-specific settlement/consumption at build/preview; authorized existing reference reuse or new clean recordings where those are missing; independent listening references, owner/native listening and explicit acceptance/budget decisions. The harness does not make any of these facts true. Reverse the preparation priority if a tested generic adapter already exists in the final integrated source, or if the owner declines comparative listening; then do not create duplicate infrastructure.

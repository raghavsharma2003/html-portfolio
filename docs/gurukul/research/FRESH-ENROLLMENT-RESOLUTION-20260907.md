# Fresh enrollment resolution, 2026-09-07

Status: read-only design, not implemented. Source inspected in `scratchpad/expert-integration` during the frozen release 11 checkpoint `f22bc6e0`. No database, provider, cloud configuration, deployment, or accuracy tests were run for this report. Source paths below are relative to that integration worktree. Configuration names and deployment documents establish requirements, not current deployed readiness.

## Decision

The existing document/face route is the smallest architectural solution **if its independent document review service, Azure Face integration, and private-source transport can be made operational**. It already establishes identity before the first voice genome and preserves every ordinary training/synthesis guard. Do not build a pre-identity genome or relax the ordinary build lease to solve this dependency.

If the intended product path is voice comparison, introduce a separate, short-lived, verification-only comparison-reference artifact. This breaks the computational circle but does not establish age or document authenticity. It therefore does not remove the independent age evidence prerequisite or make fresh enrollment operational by itself. This route requires a new reference authority contract and lifecycle before connecting the existing pure speech and byte-adapter prerequisites.

Reversal condition: a verified deployment and actual fresh-user trace through document submission, face session, deletion receipt, identity settlement, and ordinary draft creation would make the separate reference unnecessary for bootstrapping. Conversely, a deliberate product requirement to establish same-speaker continuity without using face verification would justify the separate reference work; its acceptance policy still requires measured adversarial evidence.

The self-test auto-grant in `api/_replica-processing/runtime.js:115` is conditional on self-test mode. It is not a legitimate production bootstrap alternative and is excluded here.

## Existing independent route and its limits

The route has real API callers, not only provider definitions:

- `api/replica-identity.js:35` submits to `submitOwnedIdentityCase` (`api/_replica-identity.js:114`). An owned, quarantined identity document can be submitted without a genome or prior identity. `api/replica-identity-sweep.js:20-23` obtains the configured verifier and runs the sweep.
- Document success becomes `evidence_ready`. `api/_replica-identity.js:323-337` stores adult/authentic/current/face-reference evidence and sets age plus credential expiry; it does **not** set identity/liveness.
- `api/replica-liveness.js:62` issues a challenge, with face-session actions at `:94,107`. `api/_replica-liveness.js:132` requires current adult/authentic document evidence and a face reference, without a voice genome. `api/replica-liveness-sweep.js:20` supplies the configured verifier.
- `api/_replica-liveness-verification.js:332-395` binds owner/source/document/session evidence, including provider deletion and matching reference commitments. Its final update at `:389-395` establishes identity/liveness with existing age evidence. Ordinary reviewed draft construction can then proceed.

However, deployment readiness was not established:

- `api/_identity/registry.js:3`, `api/_liveness/registry.js:3`, and `api/_face-session/registry.js:3` return no configured provider when their respective selection variables are absent. Supported implementations are the Azure identity composite, Face/Speech composite, and Face quicklink broker.
- Identity configuration requires both `AZURE_COMPOSITE_IDENTITY_ENABLED` and `AZURE_IDENTITY_REVIEW_PATH_APPROVED`; liveness requires its enable flag and the explicit limited-access flag. These are source requirements, not evidence that current approval/configuration exists or is absent.
- `services/azure-verifier/README.md:86` requires an independent review service with a meaningful human escalation path before declaring the review path approved. `docs/gurukul/DEPLOY.md:372-376` records that `/v1/document/review` is not implemented as a service or API route in this repository. The broker's `src/review.js` calls that separately authenticated service; Document Intelligence extraction is not an authenticity decision.
- `services/azure-verifier/src/config.js:58` accepts private-source origins only under Supabase host families. The active expert development storage path uses Azure Blob. The existing broker cannot consume that path by simply setting its current source-origin variable to Blob. A bounded transport change must support the exact private Azure origin and existing signed source/hash constraints, without general URL fetching.
- Document photos can supply a Face reference; the service documentation explicitly does not promise a usable Face reference for PDF input. A document-upload UI that accepts PDF alone cannot promise the face path will complete.

Minimum work for this route is therefore: implement or establish the independent authenticated document-review service; adapt the verifier's private-source validation to the actual Azure storage contract; verify supported document media; verify real Face/session/erasure configuration and callers; run a fresh-owner flow. Do not set readiness flags from the existence of source adapters.

**Preferred next step:** pursue this existing independent identity route first, because it supplies both adult-document evidence and face identity without a new reference/challenge authority. The first bounded implementation task is private Azure Blob document transport in `services/azure-verifier/src/config.js`, `src/media.js`, and their focused tests. In addition to the host restriction, `media.js:13` currently requires the Supabase `/storage/v1/object/` path. Add a separately validated exact Azure account/container/path contract and keep origin, short capability expiry, no-redirect, byte-count, MIME, and content-hash checks. Use injected real-byte fetch responses and negative controls for alternate hosts/containers/paths, URL credentials, redirects, expired capabilities, and wrong bytes. Preserve the existing Supabase contract where still supported. Do not change enable/approval flags or make provider calls in this patch. In parallel with implementation planning, the parent can establish the actual independent-review and Face deployment evidence; transport completion alone leaves those prerequisites unresolved. If that route is deliberately ruled out, the first bounded task for the comparison alternative is its pure preparation contract plus state/schema design, not enabling identity settlement.

## Separate verification-only reference: proposed implementation boundary

Use a new `vy_replica_identity_reference` authority, not a draft genome, synthetic processing job, or invented storage locator. A reference becoming ready must not update `identity_verified_at`, `liveness_verified_at`, age, training consent, selected voice artifacts, or genome tables.

Proposed files and responsibilities:

| Boundary | Proposed work |
| --- | --- |
| New `api/_voice-identity/reference-contract.js` | Strict, immutable preparation contract: owner/replica/reference UUIDs, purpose, source slots, expiry, scoped consent receipt hash, transform/model compatibility profile, and canonical commitment. Keep it distinct from an issued challenge. |
| New `api/_replica-identity-reference.js` | Owner issue/upload/finalize/status/cancel functions; exact source/hash bindings; bounded retries and token-fenced worker lease; immutable ready reference and one-time challenge reservation/consumption. |
| New API route and sweep, explicitly registered in the existing worker/cron orchestration | Make reference preparation reachable and cleanup runnable. A definition without a caller is incomplete. Return honest preparing/unavailable states. |
| New migration and `db/schema.sql` mirror | Add the reference authority and constrained source membership/consent/lease/expiry fields, plus owner reach/erasure coverage. Recheck the migration inventory at implementation time. Do not reserve a stale number here. |
| `api/_replica-processing/providers/azure-voice-evidence.js:342` and `_voice-identity/identity-audio.js` validator | Reuse the signed private-input decoder/evidence primitive only with explicitly versioned preparation semantics. Its wire key is currently `challenge_contract_sha256`; do not fabricate a challenge or silently reinterpret authority. Either explicitly extend the versioned contract for preparation or add a separately named operation with the same primitive. |
| `api/_voice-identity/issued-contract.js`, a new challenge contract version, and `_replica-voice-identity.js` | Bind `reference_kind`, reference ID, immutable reference hash, model revisions, and source ancestry at issue/lease/settlement. Existing contracts and migration 137 require a real positive genome version; do not use zero, fake versions, or weaken their constraints. Preserve legacy genome rows under their existing contract. |
| `api/_asr/providers/azure-speech-short.js` and pure `speech-v2.js` | Use verified canonical bytes and exact issued locale. Retain canonical/transport commitments, strict nonce handling and script outcomes. These prerequisites do not themselves authorize identity acceptance. |
| Owner capture UI | Add the preparation state and capture request only after a reachable backend exists. A ready reference is presented as prepared verification evidence, never as a ready voice or verified identity. |

Suggested lifecycle: `issued -> captured -> deriving -> ready -> reserved -> consumed`, with terminal `failed`, `expired`, and `revoked`. Capture finalization verifies each source's real stored bytes. Derivation is leased and retries only under the same preparation authority. Challenge issuance atomically reserves a ready, unexpired reference; failed insertion must not strand or consume it. One reference is bound to one challenge, and terminal challenge outcomes dispose of it. The preparation expiry must be finite, explicit, and committed; choose the product retention duration before implementation rather than silently borrowing a training retention policy.

Reference consent must specifically authorize biometric comparison, with capture/storage consent and an expiry. The existing `vy_replica_biometric_verification_grant` (`db/schema.sql:1562`) is foreign-keyed to **face liveness challenge** tuples. It cannot be attached to arbitrary voice/reference IDs without a schema change. Prefer an explicit reference-scoped consent receipt in the new authority rather than manufacturing a face challenge or granting training permission.

The evidence-count issue is substantive: `identity_audio_v1` accepts one capture and supplies one embedding per family. Two families are not two independent reference windows. The existing decision policy requires at least two reference windows (`api/_replica-voice-identity.js:128,333`). A minimal preparation design can request two distinct, bounded captures and retain their separately bound vectors; alternatively a real window-extraction operation is required. Do not duplicate one vector or lower the threshold to make the flow pass. Treat whether this capture design supports the existing decision calibration as an unresolved acceptance gate, not measured compatibility.

Current revision propagation is better than older notes imply: `azure-voice-evidence.js:297-314` validates and attaches actual model revisions, and the worker/builders preserve supplied revisions. Historical references without them remain unproven; do not backfill a present-day revision onto old vectors. New preparation references require actual compatible revisions and matching decoder/transform commitments at comparison.

Age remains a separate gate. Current voice settlement requires `r.age_verified_at is not null` before writing identity (`api/_replica-voice-identity.js:935-936`). A new reference cannot supply adult evidence or authenticate a legal document. Preserve that requirement and define how current credential evidence is bound in the new settlement; absence must remain an explicit prerequisite failure.

## Disposal and authority rules

- Logically revoke immediately on owner cancellation, consent withdrawal, source deletion, expiry, replica revocation, or terminal challenge outcome. Stale leases must not publish ready references or accept challenges afterward. Define and test lock ordering for concurrent revocation/settlement; plain snapshot predicates alone do not prove serialized protection.
- Keep canonical decoded audio in process only where possible; release it on success, failure, timeout, and cancellation. Store only the temporary vectors and bounded commitments required for comparison. Vectors are sensitive biometric evidence, not content-free telemetry.
- Delete temporary vectors when consumed or otherwise terminal. Mark reference/capture source objects for the existing deletion machinery. Honor signed-upload writer fences before physical deletion so an outstanding upload cannot recreate an erased object. Retain only explicitly bounded audit commitments, with person erasure covering even those.
- If reusing the existing `identity_challenge` source category, bind a server-authorized reference role and membership in the new authority. Do not permit arbitrary generic upload claims to create reference membership. `finalizeOwnedSource` must continue to exclude this category from ordinary enrollment jobs. A new source category instead requires all source-purpose/schema/erasure inventories to change; make that choice explicit.
- Do not insert verification outputs into ordinary processing artifact tables with a fabricated processing-job provenance. Do not promote these captures into training references as a side effect of successful identity; ordinary selection, review, build, and synthesis guards still apply.

## Required evidence before enabling

1. Actual-function offline tests: fresh owner can prepare a comparison reference while ordinary selection/build/preview/runtime still reject missing identity; reference readiness never changes identity or age. A negative control that removes the ordinary guard must fail these assertions.
2. Byte/authority tests: owner/replica/source swaps, source hash drift, duplicate capture ancestry, stale leases, unknown revision, wrong-family vectors, one-reference evidence, replaced reference, changed preparation/issued contracts, expired or revoked consent, and different locales fail before dispatch or settlement as appropriate. Reusing the challenge capture itself as a reference must fail.
3. Speech controls retain exact issued nonce and script semantics. Missing age cannot result in identity even with matching speaker/speech. Test outcomes as separate preparation, speech match, comparison evidence, and final identity states.
4. Real PostgreSQL EXPLAIN for each actual changed statement, plus disposable exact-dev fixtures asserting resulting row/source states for expiry, duplicate issuance, canceled preparation, retry, and success. Mocks establish control flow only. Exercise concurrent lease/revocation/settlement interleavings if serial revocation protection is claimed.
5. Erasure tests include failed preparation, abandoned uploads, active upload capabilities, pending challenge, consumed reference, worker restart, and whole-person deletion. Register the new owner lane in `scripts/relcheck.mjs` and the erasure cascade.
6. Deployment evidence verifies real route/sweep callers, storage origin, signing/response seals, timeouts, and deletion receipts. Provider success/voice accuracy must come from authorized real calls and a stated acceptance set, not injected transports. Until that evidence and policy review exist, keep the new acceptance profile disabled.

Rejected shortcuts: removing identity predicates from ordinary model builds; writing a fake draft genome solely for verification; treating document OCR as authenticity; copying one embedding twice; stamping old vectors with a current revision; treating a contract hash or `speech_matched` as identity acceptance. Each hides rather than resolves a distinct missing authority or measurement.

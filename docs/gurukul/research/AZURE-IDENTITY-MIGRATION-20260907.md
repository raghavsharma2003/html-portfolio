# Azure voice challenge migration draft

Date: 2026-09-07. Read-only design against integration checkpoint `3bf53790` while release run 6 is frozen. No integration files, database rows, cloud resources, keys, model calls or recordings changed. This draft is outside the integration tree. It is not a voice accuracy or identity acceptance result.

## Recommended boundary

Use a new, explicitly versioned Azure voice-challenge verifier and issue-time recognition contract. Do not replace Sarvam with Azure in the existing verifier and pass its `unknown` hint through. Keep Azure-only challenge verification disabled until language, exact reference, same-source audio and settlement bindings are implemented and tested. An Azure resource being available establishes configuration capability, not identity assurance.

For the first language contract, use a server-owned bank of fixed-language challenges: `hi-IN` with authored Devanagari text and `en-IN` with English text. The owner explicitly chooses the offered challenge language at issuance. The server validates the enum and chooses a bank entry; subsequent capture/verify requests cannot override that language. A Roman Hindi display can be a separately authored display variant of the same bank item with an exact canonical Hindi scoring string. It must not be generated by an LLM or guessed from the transcript. Leave code-switched challenges unaccepted until their own normalization and recognition tests exist. This deliberately concerns the identity ceremony only, not the languages the expert may speak in conversations.

## Minimal schema and receipt proposal

Keep existing tables and their erasure coverage. Use the next verified free migration number only after release unfreezes; this draft reserves no number. Add nullable fields for compatibility, then require them for the new `challenge_policy` version with a SQL CHECK:

- `recognition_locale text`: exact allowlist `hi-IN` or `en-IN` for the new policy.
- `sentence_bank_item text`: immutable, versioned item ID, including selected display variant. The code registry maps it to locale and canonical/display text; changes require a new ID.
- `verification_profile text`: immutable profile ID describing Azure ASR adapter contract, input transform, normalizer and decision policy. It identifies the supported interpretation of this challenge.
- `challenge_contract_hash text`: SHA-256 of canonical JSON covering schema version, challenge ID, locale, bank item, sentence hash, nonce hash, selected reference-genome version, challenge policy and verifier profile. This supplements the existing sentence hash rather than relabeling it.

The profile can carry fixed code revision identifiers rather than duplicating every version in SQL columns. Extend the decision-basis whitelist with scalar `recognition_locale`, `asr_provider`, `asr_adapter_version`, `asr_api_contract`, `recognizer_revision_status`, `normalizer_version`, `verification_profile`, `challenge_contract_hash`, `transcript_script_relation`, and exact same-source transform commitments. Keep the 4 KiB bound and forbid transcripts, URLs, vectors and credentials. Add exact typed validation, not only safe key names.

The existing Azure provider's `azure-speech-short-v1` is a local adapter label, not a Microsoft acoustic-weight revision. Short REST exposes no immutable recognizer model ID in the inspected request/response contract. Record `recognizer_revision_status=not_exposed` honestly, plus actual adapter/profile/API path/resource binding. Do not invent a cloud model hash. If product acceptance requires immutable acoustic weights, this short endpoint cannot meet that requirement merely by changing its local version string; use an eligible model-pinned Azure route as a separate measured migration.

Do not backfill locale/profile on v1 rows by guessing. Preserve completed historical evidence unchanged. New Azure workers lease only supported new-policy/profile rows. Old uncompleted ceremonies need a named reissue/expiry path with existing source-erasure fences; they must not be reinterpreted or stranded invisibly. Keep legacy non-Azure workers out of the new policy with an explicit supported-policy predicate.

No new identity bypass or manual approve endpoint is needed. Existing identity timestamp updates remain restricted to a valid `accept` settlement and retain the age check.

## Code changes after the freeze

1. **Issue and client contract:** change the bank from strings to immutable typed entries. Accept only an explicit selected challenge locale on the authenticated issue route. Validate server capability/profile before inserting a ceremony that cannot be processed. Return the stored locale and display text. Update both Studio namespace API/types/UI if still mounted; changing a UI preference after issuance changes only the next challenge. Keep rate limits, supersession, source-use consents and the three-minute capture/finalize deadline.
2. **Lease and settlement:** include locale, bank item, contract hash, profile, challenge policy and issued reference version in lease data. Select compatible policy/profile before leasing; validate all bindings before wake. Settlement compares them to the stored row and attempt, alongside existing owner/source-hash/lease-token/expiry predicates. Recheck source authority/consent and exact reference eligibility at settlement so revocation during a provider call cannot open identity. Passing an in-memory lease alone is insufficient proof of the issued contract.
3. **One audio authority:** use a server-side capture-derived audio artifact with a signed commitment over capture SHA, audio SHA, transform version and decoded duration. Feed that audio to both speaker evidence and the Azure transport derivative. Reuse existing Azure voice-evidence/media mechanisms where they provide the necessary bytes and receipt; this audit did not prove that exact transform output endpoint exists. Reject swapped capture/transcript objects even when each independently hashes correctly. Keep raw/derived objects under source erasure and never promote identity audio into enrollment material.
4. **Dedicated Azure verifier:** instantiate Azure Speech directly under the permitted Azure-origin policy, not the general live-ASR selector that may change strategy. Assert exact `hi-IN`/`en-IN`, compatible profile and receipt fields before work. Preserve wake-before-sign for evidence, hash-verified private reads and redirect refusal. Keep locale in the result as requested, not detected. Carry provider and transform identity through `runVoiceChallengeSweep`, which currently drops all ASR metadata except text.
5. **Versioned decision:** do not lower any voice threshold or remove nonce requirements. Check reference sufficiency and mandatory exact nonce first; a failed nonce remains reject even at perfect speaker similarity. Low speaker similarity remains reject even when transcript script differs. With nonce present and sufficient voice evidence, a known script mismatch becomes review/inconclusive, never accept. Same-script genuinely wrong sentence remains reject; uncertain/unsupported normalization cannot be upgraded by arbitrary transliteration. Do not cherry-pick another locale or N-best transcript because it best matches the expected nonce. Expected text/nonce must never be sent as a recognition prompt or phrase bias.
6. **Receipts and UI:** distinguish retryable provider/configuration failure from settled inconclusive transcription. Add a named ASR/script-review reason that says the system could not verify the words, without asserting the owner read them wrongly. `review` continues to leave all identity gates closed. Remove any promise of human review unless its durable queue and retention/consent policy exist.

For digit words such as “one two” versus normalized numeric output, first retain deterministic Display/ITN behavior as a named profile. Missing six-digit proof cannot pass. Any word-to-digit parser must be locale-specific, finite and independently tested, with a new normalizer version; do not use a generative judge to recover the expected code. The initial profile may remain inconclusive on unsupported forms.

## Microsoft contract check

The short REST contract requires an explicit language, accepts at most 60 seconds, and supports mono 16 kHz PCM WAV. It returns final results; detailed responses offer lexical and normalized display forms. These facts support a fixed-locale, server-verified 24-to-16 kHz transport derivative, not an `unknown` or auto-detected identity hint. [Microsoft short-audio REST documentation](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/rest-speech-to-text-short).

SDK language identification accepts up to four candidates at start and ten continuously, can choose a candidate even when none match the actual speech, and does not identify word-level switches within one sentence. Therefore LID is not a substitute for the language contract of a server-authored identity challenge. [Microsoft language identification](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/language-identification).

Batch LID is a different asynchronous contract with candidate locales. Combining it with a custom model falls back to base models according to Microsoft; it also changes storage, retention and job lifecycle. It is not a minimal replacement for the existing short challenge verifier. [Microsoft batch transcription](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/batch-transcription-create).

## Required tests, with negative controls

These are proposed tests, not run results.

- Issue both supported locales deterministically; assert exact bank/display/locale/reference/profile hash. Reject omitted/unknown/auto locale and forged bank text. Changing locale after issue must not alter the worker request.
- Apply the idempotent migration to the isolated database only; run real EXPLAIN for issue, lease and settlement. Seed v1, supported v2 and unsupported-profile rows: only the compatible v2 row leases. No guessed legacy backfill.
- Change locale, profile, reference version, sentence/contract hash, verifier revision, source SHA or consent between issue/lease/settle: no verified mutation. Expired token, superseded attempt, wrong owner and source deletion still fail. Positive settlement prevents “always reject” from passing.
- Exercise the actual Azure adapter with injected transport: exact locale/query, redirect error, verified 16 kHz payload, original 24 kHz commitment unchanged, measured 30-second cap, correct requested-language provenance. Unsupported locale and invalid audio refuse before network or GPU wake. HTTP/NoMatch/timeout cannot produce empty-transcript acceptance or external fallback.
- Preserve fresh nonce, wrong nonce, missing nonce, one changed digit, leading zero and folded Indic digit controls. Add six digits embedded in a longer number, digits split by words, reordered digits, and distractor number cases. Remove nonce enforcement in a negative-control policy and demonstrate that replay protection breaks.
- Same source passes the transport binding; independently valid hashes from two different recordings fail. Removing the parent capture/audio transform commitment in a negative control must make that attack fixture pass and therefore fail the gate.
- Script mismatch plus correct nonce and high similarity yields review with identity timestamps untouched. The same mismatch with missing nonce or low similarity remains reject. Perfect same-script controlled evidence can traverse the positive path. No claim of false-accept rate follows from these fixtures.
- Basis contains only allowlisted scalar metrics/commitments and fits its size bound. Review, rejection, cancellation and accepted completion preserve source erasure; UI does not promise an unimplemented human-review consumer.

After code/SQL gates, obtain an authorized, bounded real Azure speech pack across the chosen locales, native scripts, digit styles and microphone conditions, plus impostor and replay controls. Pre-register acceptance criteria and retain exact provider/profile/input/output commitments and outcomes. Existing ECAPA thresholds and the transcript-overlap threshold have no Azure-specific identity-error calibration in this audit. Keep that limitation visible; a successful Azure transcript is not a measured identity guarantee.

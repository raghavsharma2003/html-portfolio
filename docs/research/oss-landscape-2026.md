## Open-source realtime voice-agent stacks (Pipecat, LiveKit Agents, Vocode, TEN, Gemini Live/OpenAI Realtime) — turn-taking, barge-in, and noise robustness, distilled into 5 mechanisms Meera's hand-rolled Gemini-Live call lane should adopt

- **docs.pipecat.ai/pipecat-cloud/guides/smart-turn** [verified-in-source]
  Two-stage turn-end gate: cheap VAD (Silero) fires fast on speech->silence (stop_secs default 0.2s), but that ONLY arms a second, semantic classifier — Smart Turn — which is a small model (Whisper-Tiny backbone + linear head, ~8M params, int8 8MB) fed the raw 16kHz waveform of the whole candidate utterance (up to 8s, front-padded if shorter). Smart Turn runs ONLY during the silence window VAD just opened (not continuously), so it costs nothing while the user is actively talking. Inference is 10ms-100ms CPU (65ms measured on Pipecat Cloud). It judges completion from grammar/intonation/pace in the raw audio, not the transcript, so disfluencies, trailing-off, and background noise during the pause don't get misread as silence-therefore-done the way naive VAD-only endpointing does.
  - _why it matters here:_ CLAUDE.md's liveCall.ts constraint (import nothing beyond ./level and ../engine/diag) means Meera can't pull in a whole framework, but this pattern is copyable as a small local gate: keep whatever VAD/silence signal already exists to trigger candidate turn-end, then before firing the actual Gemini-Live turn-end/response, run one extra cheap check against the buffered audio rather than committing the instant silence is detected — directly targets 'not aborting mid-sentence under noise'.
- **livekit.com/blog/adaptive-interruption-handling** [verified-in-source]
  Interrupt classifier gates barge-in itself, separate from turn-end detection. When the agent is speaking and VAD detects incoming user audio, the system does NOT immediately cut the agent's TTS. Instead it runs a small CNN-over-audio-encoder model on just the first ~216ms of the detected speech onset, looking at onset sharpness/strength, signal duration, and short-window prosody (pitch/rhythm), trained on hundreds of hours of human-human speech augmented with noise. Only if that model says 'this is a real speech onset, not a cough/backchannel/noise burst' does it send the cancel-and-stop-audio signal. Measured result: rejects 51% of VAD-only false-positive barge-ins while keeping 100% recall on real interruptions, at 30ms inference.
  - _why it matters here:_ This is the single most direct mechanism for 'not aborting mid-sentence under noise' AND fast turn ends without hurting barge-in responsiveness: gate the abort-agent-speech action on a short onset-classification window (~150-250ms of incoming audio) instead of firing on the very first VAD-positive frame. On phone mics (background chatter, coughs, 'hmm'), this is what stops Meera's voice from cutting off her own sentence on every stray noise.
- **livekit.com/blog/using-a-transformer-to-improve-end-of-turn-detection** [verified-in-source]
  Semantic end-of-utterance model dynamically shortens/lengthens the VAD silence timeout rather than using a fixed stop_secs. A compact transformer (135M params, SmolLM-v2-based, CPU-real-time, 4-turn sliding context window over STT partials) scores each incremental transcript for 'is this turn actually over' (e.g. recognizes 'I understand your point, but…' as unfinished despite a pause). High-confidence-done -> short wait before responding; low-confidence/trailing-conjunction -> the silence timeout is extended before the system commits to ending the user's turn. Measured: -85% unintentional interruptions, only 3% false 'not done yet' rate, ~50ms inference.
  - _why it matters here:_ Directly gives 'fast turn ends' without the noise-abort tradeoff: instead of one fixed silence-duration threshold for deciding the user is done (which is what likely causes both premature cutoffs on pauses AND slow responses on clear endings), make the wait-before-committing variable based on a lightweight semantic/lexical signal (even a cheap heuristic on trailing words/punctuation-equivalent prosody cues) — short timeout on clear sentence-final shapes, longer timeout after conjunctions/fillers/trailing pitch.
- **platform.openai.com/docs/guides/realtime-vad + developers.openai.com/api/docs/guides/realtime-conversations** [reported]
  OpenAI Realtime's semantic_vad turn_detection mode ships this exact same dynamic-timeout idea as a first-class API parameter (as opposed to LiveKit's bolt-on model): it estimates completion probability continuously and sets the end-of-turn wait based on that probability, e.g. a trailing 'ummm' gets a longer timeout than a definitive statement. Separately, interrupt_response and create_response can be decoupled from VAD (turn_detection.interrupt_response=false) so an app can get 'notice speech started' without immediately auto-truncating/cancelling agent audio, letting the app apply its own onset-confidence gate before acting — and OpenAI's transport layer tracks exactly how much output audio has actually played so truncation is sample-accurate rather than an estimate.
  - _why it matters here:_ Reported (not directly fetched from a primary spec page), but corroborates the same two-signal pattern (dynamic timeout + decoupled 'speech detected' vs 'act on it') independently at the API-protocol level, suggesting Meera's Gemini-Live lane should track exact agent-audio-played-position itself (for accurate truncation) and treat 'VAD said speech started' and 'commit to interrupting' as two separate decisions rather than one signal, mirroring liveCall.ts's likely existing audio pipeline.
- **docs.pipecat.ai/pipecat-cloud/guides/smart-turn** [reported]
  Explicit backchannel/filler allowlist checked against the recognized text (not just audio energy) before treating incoming user speech as an interruption: short tokens like 'mhm', 'yeah', 'okay', 'right', 'haan', 'hmm' that arrive while the agent is talking are matched against a small ignore-list; if the utterance is short (sub-second) AND matches the list AND doesn't continue into more words, it is logged as a backchannel acknowledgment and does NOT trigger response cancellation — the agent keeps talking through it. This is combined with the onset-classifier (finding 2) as an additional lexical filter layer, and is also the missing half of the 'natural backchannels' requirement: without this, systems can also decide to actively emit their own short affirmations during long user turns and gate those affirmations so they never contain content, only proven-empty filler tokens.
  - _why it matters here:_ Given CLAUDE.md's persona rule that 'anything sentence-shaped in a prompt gets recited,' the backchannel-emission half must stay strictly non-lexical/local (a fixed small pool of short Hinglish filler tokens like 'haan', 'hmm', 'arre'), not LLM-generated — otherwise it risks becoming rehearsed lines, the exact failure mode the codebase already logged as a persona lesson. On the listening side, a fixed ignore-list of backchannel tokens is cheap, deterministic, and directly stops Meera from aborting her own sentence when the user just says 'hmm' or 'haan' mid-response.

**Top actions:**
- Add a two-stage turn-end gate to liveCall.ts's silence handling: keep the fast VAD/silence trigger as-is, but before committing to end-of-turn, buffer the last ~1-2s of audio and require either (a) a short cheap classifier pass or (b) at minimum a variable timeout keyed to simple trailing-word/prosody heuristics (longer wait after conjunctions/fillers, shorter after clear sentence-final shapes) — this is the single highest-leverage fix for both 'not aborting mid-sentence' and 'fast turn ends' simultaneously, per LiveKit's measured -85% interruptions / 3% false-wait tradeoff.
- Decouple 'speech onset detected' from 'abort agent audio': gate the actual TTS-cancel/interrupt action on ~150-250ms of confirmed onset (duration + energy-rise shape, or the OpenAI-style semantic_vad-equivalent) plus a lexical backchannel-ignore list (mhm/haan/yeah/hmm/okay), rather than firing cancellation on the first VAD-positive frame — directly stops phone-mic noise and short acknowledgments from cutting Meera off mid-sentence, matching LiveKit's measured 51% false-positive-barge-in rejection at 100% recall.
- Track exact agent-audio-played-position in liveCall.ts's playback path so any interruption that IS accepted truncates precisely at what the user actually heard (not an estimate) — this is what OpenAI Realtime's transport layer and Gemini Live's own interrupted-event handling both rely on, and it's a prerequisite for the conversation history staying consistent after a real barge-in. For backchannels Meera emits herself, restrict to a small fixed non-LLM-generated token pool (never phrase-shaped LLM output) per the persona.ts lesson that sentence-shaped prompt content gets recited verbatim.

## Open-source AI companion apps/frameworks (2026): mechanisms worth stealing for Meera's Hinglish companion + relational memory OS

- **SillyTavern** [verified-in-source]
  World Info / lorebook activation engine: entries fire on keyword match (case-insensitive, optional whole-word, optional JS-style /regex/) against chat text OR against character description/personality/scenario/persona description/creator's notes. Secondary-key filters use boolean logic (AND ANY / AND ALL / NOT ANY / NOT ALL) so an entry can require two concepts co-occurring before firing. Entries can trigger other entries (recursion) with three per-entry modes: non-recursable, prevent-further-recursion, delay-until-recursion; global caps are Max Recursion Steps and Min Activations. Budget is a token cap or % of context; constant entries insert first, then remaining entries by insertion-order number, and once the budget is exhausted no more entries insert regardless of keyword match. Placement is per-entry: before/after character defs, before/after examples, top/bottom of author's note, or @Depth N with a role. Timed effects (measured in message-count, not tokens): Sticky (stays active N messages after firing), Cooldown (can't refire for N messages), Delay (can't fire until N messages have passed). Trigger Probability adds a %-chance to suppress an otherwise-activated entry, for randomized callbacks.
  - _why it matters here:_ This is a directly implementable pattern for Meera's relational-memory-OS retrieval layer: instead of pure vector-similarity recall, gate memory-graph nodes by (a) keyword/entity match against recent turns AND persona-slot text, (b) recursion so recalling one memory can surface linked memories (mirrors a relational graph edge-walk), (c) a hard token budget with priority ordering so the newest/highest-priority facts always win under prompt-budget pressure (directly analogous to Meera's own prompt-budget slicing problem noted in CLAUDE.md), and (d) message-count-based sticky/cooldown windows to stop the same callback recurring every turn — a cheap fix for repetitive-recall failure modes.
- **SillyTavern** [verified-in-source]
  Group chat speaker selection has four strategies: Natural Order (extract whole-word name mentions from the latest message → activate mentioned characters → else activate by each character's 'talkativeness' stat, a 0-100% linear dial from Shy/never-unless-mentioned to Chatty/always-replies, default 50% → else pick randomly among unmuted members), List Order (fixed round-robin per member list position), Pooled Order (cycle everyone who hasn't spoken since the last user message, then reshuffle once the pool empties), and Manual (explicit pick or /trigger). Context assembly has two modes: 'swap cards' (only the active speaker's persona enters context, default, cheapest) vs 'join cards' (all members' persona blocks concatenated with configurable separators, optionally excluding muted members).
  - _why it matters here:_ Meera's games centre / any future multi-persona or multi-user surface can reuse 'talkativeness' as a tunable proactivity knob per context (e.g., how eagerly she interjects during screen-share vs. text chat) and 'swap vs join cards' as a direct pattern for context-window management when the memory OS must decide whether to inject one relationship-node's full profile or a compressed multi-node summary — cheap lever for the prompt-budget gate already enforced by scripts/check-prompt-budget.mjs.
- **Character Card V2 spec** [verified-in-source]
  Persona is a flat JSON `data` object: name, description, personality, scenario, first_mes, mes_example (carried from v1) plus system_prompt (overrides the app's global system prompt when present), post_history_instructions (injected AFTER the conversation history, not before — so it survives context truncation from the front), alternate_greetings (array, lets a single card open a conversation multiple different ways), creator_notes/tags/creator/character_version (excluded from the actual prompt, purely for humans), and an `extensions` object at both card level and entry level that frontends must preserve even for keys they don't understand (forward-compatible custom fields). A `character_book` (an embedded lorebook, same schema as standalone World Info) ships inside the card itself and is explicitly specified to stack with, not replace, any global lorebook — character_book entries get scanned/budgeted first, then global entries fill remaining budget.
  - _why it matters here:_ Two things worth stealing directly: (1) post_history_instructions' 'inject after history, not before' placement is the same fix CLAUDE.md already discovered independently for persona.ts (rules appended last fire 8/8 vs buried mid-brief firing 0/8) — validates that pattern is a known cross-project mechanism, not a one-off finding, and suggests any NEVER-rule (crisis lines, never-deny-AI) should literally live in a post_history_instructions-equivalent slot. (2) extensions-must-survive-unknown-keys is a good forward-compat contract for Meera's own persona-compiler output format if it's ever versioned or exported.
- **AIRI / Project AIRI** [verified-in-source]
  Storage architecture is explicitly two-tier: client-side pure-browser DB (DuckDB WASM / PGLite) for local-first/offline operation, plus a server-side Postgres+pgvector package (@proj-airi/memory-pgvector) for semantic/vector recall — the two are wired through separate DBDriver and MemoryDriver abstraction layers feeding a shared 'Core' orchestrator, so the same character logic runs whether memory is local WASM or a hosted pgvector instance. It also runs as three deployment targets from one core (Stage Web PWA, Stage Tamagotchi desktop/Electron with native CUDA/Metal accel, Stage Pocket mobile via Capacitor) and integrates real task-execution loops (autonomously plays Minecraft/Factorio) rather than pure chat.
  - _why it matters here:_ The DBDriver/MemoryDriver split is a clean architectural precedent for keeping Meera's relational memory graph swappable between a lightweight/offline mode and the full Postgres relational-memory-OS — useful if Meera ever needs an offline-degraded mode on the Android APK build. The Capacitor multi-target-from-one-core pattern also directly parallels Meera's own web+Capacitor-APK split, so AIRI's driver-abstraction boundary is a concrete reference architecture for where to draw that line.
- **Open-LLM-VTuber** [verified-in-source]
  Ships an explicit 'AI proactive speaking' feature (unprompted turn-initiation, config-gated) plus a separate 'inner thoughts' channel: the model emits expressions/thoughts/actions in a structured side-channel that renders as avatar affect/UI state WITHOUT being spoken aloud or added to the visible transcript — i.e., a second output stream parsed out of the same generation and routed to non-dialogue UI rather than TTS. Long-term memory was explicitly ripped out and is being rebuilt on Letta (formerly MemGPT) rather than a bespoke store, per the maintainers' own recent changelog language, while raw chat-log persistence (not memory) is what currently lets users resume old threads.
  - _why it matters here:_ The 'inner thoughts' side-channel is the most directly stealable mechanism here: have Meera's generation emit a structured (e.g., tagged/JSON) affect-and-intent block alongside her spoken reply, parsed server-side and used to drive things like proactive-message timing, mood state, or memory-write decisions — without that scaffolding ever reaching the user as literal text (avoiding CLAUDE.md's own documented failure mode where anything sentence-shaped in the prompt gets recited verbatim, since this channel is model OUTPUT to be parsed, not prompt input to be echoed).
- **ChatterUI** [verified-in-source]
  Mobile-first (Android, on-device via llama.cpp/gguf) frontend that decouples 'chat' from 'character' as separate entities: one Character Card v2 persona can have many independent Chat threads, each thread its own context/history, selectable from a per-character chat list — plus a distinct User/Persona editor so the human side of the conversation is also a swappable named entity, not just an implicit 'user' token. Instruct-formatting and sampler parameters are exposed as user-editable templates per backend (local llama.cpp, KoboldCpp, text-generation-webui, AI Horde, OpenRouter, etc.), decoupling the prompt-formatting layer from the model backend.
  - _why it matters here:_ The character-vs-chat-thread separation (many threads per persona, each independently resumable) is directly relevant if Meera ever supports multiple parallel conversation contexts with the same relationship (e.g., a 'fresh start' or per-topic thread) without losing the underlying relational memory graph tied to the persona itself rather than to any single thread — memory should attach to the (user, Meera) relationship node, not to the chat-thread row, mirroring how ChatterUI keeps memory/persona and thread as separate entities.
- **RealChar** [reported]
  Multimodal realtime pipeline (Whisper STT -> LLM -> ElevenLabs TTS) wired through Chroma vector DB + LlamaIndex for retrieval, offered as 'modular, swap any component' rather than a monolith; the team since pivoted to a commercial spinout (ReByte.ai) and search results show no confirmed recent commit/release activity in 2025-2026, i.e. likely dormant.
  - _why it matters here:_ Lower value than the others — flag as legacy reference only: the swap-any-component modularity is a reasonable design goal but the project itself appears inactive, so treat it as a historical data point (early open-source realtime-companion pipeline shape) rather than a current best-practice source.
- **Amica / heyamica.com + semperai/arbius ecosystem — reported via search only, not directly fetched from primary repo** [reported]
  Described as having an 'emotion engine' that lets the avatar 'express feelings, complete tasks and engage on her own' with swappable voice/personality/graphics/model layers; exact emotion-state-machine implementation was not available in the pages actually fetched.
  - _why it matters here:_ The emotion-engine claim is a good conceptual parallel to Meera's own affect handling but the underlying mechanism (state representation, trigger rules) could not be verified from a primary source in this pass, so it should not be treated as implementable without further direct repo inspection.

## chess-board-ux

- **github.com/lichess-org/chessground src/state.ts** [verified-in-source]
  Default HeadlessState: animation.enabled=true, animation.duration=200 (ms). draggable.enabled=true, draggable.distance=3 (px), draggable.autoDistance=true, draggable.showGhost=true, draggable.deleteOnDropOff=false. premovable.enabled=true, premovable.showDests=true, premovable.castle=true. movable.free=true, movable.color='both', movable.showDests=true, movable.rookCastle=true. touchIgnoreRadius=1, coordinates=true, coordinatesOnSquares=false, autoCastle=true, viewOnly=false, ranksPosition='right'.
  - _why it matters here:_ These are the exact numeric defaults to replicate for a local chess game module: 200ms piece-move animation, 3px drag-start threshold, ghost piece shown while dragging, premoves/predrops on by default. Implementable verbatim.
- **github.com/lichess-org/chessground src/config.ts** [verified-in-source]
  Guard clause: if (state.animation.duration || 0) < 70, animation.enabled is forced false. So durations below 70ms are treated as effectively instant/disabled — 70ms is the practical floor for a perceptible move animation.
  - _why it matters here:_ Gives a concrete lower bound: don't animate below ~70ms or it reads as a snap, not a slide. Useful for a 'fast' animation-speed preference toggle in the games centre.
- **github.com/lichess-org/chessground src/anim.ts** [verified-in-source]
  Easing is a hand-rolled cubic ease-in-out: t<0.5 ? 4*t*t*t : (t-1)*(2*t-2)*(2*t-2)+1 (equivalent to easeInOutCubic). Duration is converted to a per-frame frequency = 1/duration; each animation frame computes rest = 1 - (now - start) * frequency and eases it via the cubic function above to interpolate piece position. Animation runs via a self-recursive requestAnimationFrame step() loop; when rest reaches <=0 the loop stops and does one final non-optimized redraw. Piece-move detection works by diffing old/new board maps: a piece missing at square A and a same-type piece appearing at square B are paired (nearest-neighbor spatial matching) and animated as a translation from A to B rather than a fade-out/fade-in; unpaired disappearing pieces go into a separate 'fadings' map and fade instead of translate (used for captures where no matching piece reappears elsewhere, and for pieces that vanish, e.g. en passant capture squares).
  - _why it matters here:_ This is the exact algorithm to implement for a premium-feeling local chess board: (1) classic easeInOutCubic, not linear, not spring; (2) moves are literal translate animations between old/new DOM positions computed via nearest-piece matching, not per-square re-render; (3) captures that don't have a reappearing same-type piece fade out at 0.5 opacity while the capturing piece is drawn on top (z-index 8 for '.anim', ghost .3 opacity, fading pieces z-index 1 / opacity 0.5, per chessground.base.css).
- **github.com/lichess-org/chessground src/drag.ts** [verified-in-source]
  Drag begins in start(): only trusted events, left-click or single-touch, and only if a draggable piece exists at the pointer square. Visual drag doesn't 'commit' until processDrag() sees squared-distance moved >= draggable.distance^2 (3px default) — this is the autoDistance threshold that prevents a light tap/click from being read as a drag. A .ghost element (opacity 0.3, from CSS) is shown at the origin square while the real piece follows the pointer via translate. On end(), destination square is resolved via getKeyAtDomPos() (pointer coords -> board coords with board orientation/size accounted for) and either dropNewPiece() or userMove() commits the move; releasing outside the board deletes the piece if deleteOnDropOff is true, otherwise the piece snaps back. Before any drag starts, existing premove/predrop state is cleared (unsetPremove/unsetPredrop) so a fresh drag always overrides a stale premove.
  - _why it matters here:_ Gives the exact interaction contract for both click-to-move and drag-to-move on a touch board: a 3px move threshold is what separates 'tap to select' from 'drag to move' on the same pointerdown, which is critical for mobile where finger jitter is much larger than mouse jitter — worth tuning this up (chess.com-style implementations commonly bump this for touch) rather than reusing 3px verbatim on Android.
- **github.com/lichess-org/lila COPYING.md** [verified-in-source]
  Lichess's default piece sets are GPLv2+: cburnett by Colin M.L. Burnett, merida by Armando Hernandez Marroquin. GPLv2+ is a strong copyleft license — using these exact SVG/PNG piece assets in a closed-source product creates a real obligation (attribution required at minimum; derivative/redistributed works arguably need to stay GPL-compatible and offer source), which is a licensing risk for a proprietary Android/web app that isn't going to open-source its games module.
  - _why it matters here:_ Actionable red flag: do NOT bundle lichess's cburnett/merida SVGs directly into Meera's proprietary app bundle without either (a) a separate compatible license/permission, or (b) commissioning/using an original or permissively-licensed (MIT/CC0) piece set instead. This is exactly the kind of licensing trap that's easy to miss when copying 'the good-looking free chess pieces' wholesale.
- **chessground.base.css** [verified-in-source]
  square.last-move gets will-change: transform (GPU hint, no visible color rule found in this file — last-move highlight color is set by board *theme* CSS, layered separately from base.css). Dragged piece gets z-index 11 !important and cursor: move. Animating pieces sit at z-index 8 (.anim). Ghost piece opacity 0.3. Fading (captured, no-reappear) pieces: z-index 1, opacity 0.5. Move-destination squares get pointer-events: auto (so only legal squares are clickable/droppable, with illegal squares inert to pointer events entirely rather than handled via JS-side rejection alone).
  - _why it matters here:_ Concrete z-index/opacity stack to copy for a layered board renderer: drag(11) > anim(8) > normal pieces > fading(1, 0.5 opacity) with ghost at origin at 0.3 opacity. Also: legal-move affordance is partly enforced at the CSS layer (pointer-events) not just JS, which is cheap and prevents mis-taps on illegal squares from even registering.
- **lila GitHub issues/forum: 'new sounds' #594, 'Check Sound Consistency' #8365, 'Request to add check move sound' #14364; public/sound directory referenced** [reported]

## State of the art (2026) in agent/companion memory systems, focused on episodic/semantic/shared-event separation, fabrication prevention, decay/consolidation, and "who was present" retrieval scoping — relevant to Meera's relational memory graph.

- **Graphiti GitHub README + docs.getzep.com core-concepts** [verified-in-source]
  Bi-temporal knowledge graph: every extracted fact is an edge with FOUR timestamps — t_created/t_expired (when the system learned/invalidated it) and t_valid/t_invalid (when it was actually true in the world). New conflicting information does NOT overwrite or merge into the old edge; the old edge's t_invalid is set (closing its validity window) and a new edge is inserted. Nothing is deleted, so point-in-time queries ('what did we believe as of date X') are answerable. Episodes (raw conversational turns/messages) are stored verbatim as the ground-truth layer; entities and edges are the derived semantic layer, and every node/edge keeps a pointer back to the source episode(s) that produced it (an explicit provenance/audit trail — 'why does the graph believe this'). Multi-tenant/multi-participant scoping is done via a `group_id` field attached to every episode and every derived node/edge, used to partition the graph per user/session/participant-set. When multiple episodes are ingested together the system concatenates them with `[Episode N]` headers + timestamps before the extraction LLM call, and tracks a node_episode_index_map so each entity mention can be attributed to the specific episode (and by extension, participant) it came from. The MCP server queues episode ingestion per group_id sequentially so ordering/attribution isn't scrambled by concurrent writes.

- **langchain-ai.github.io/langmem/concepts/conceptual_guide/** [verified-in-source]

- **arxiv.org/html/2607.22962 'ConsistencyGate: Preventing Memory Contamination in LLM Agents via Self-Consistency Admission Control'** [reported]

## Stopping confabulated shared memories / false user-claims in a prompt-compiled companion with a structured memory graph + post-generation gate

- **MemGuard — Preventing Memory Contamination in Long-Term Memory-Augmented LLMs** [reported]
  Type-aware memory framework fighting 'heterogeneous memory contamination': every memory item gets an explicit functional-role tag at write time (user-fact / episodic-event / behavioral-rule / inferred-preference), the store enforces type-isolated relations so an episodic one-off doesn't get read as a durable trait, and retrieval does 'selective evidence composition' — pulling evidence only from the memory types the current turn actually needs rather than dumping everything semantically similar into context. Reported up to 28.27% memory-reliability improvement while retrieving 5.8x fewer memory tokens than undifferentiated retrieval.
  - _why it matters here:_ Meera's Postgres memory graph almost certainly already has some node typing; this maps directly onto adding a `kind` column (fact/event/rule/inference) plus a provenance flag (`stated_by_user` vs `inferred_by_meera`) and filtering retrieval by kind per intent — e.g. never let an inferred preference be retrieved as if it were a stated fact, and never let a single mentioned event ('I went to Goa once') get retrieved as a recurring trait ('you always go to Goa'). This is a schema + retrieval-query change, not a model change.
- **HalluciNot — Hallucination Detection Through Context and Common Knowledge Verification** [reported]
  A post-generation verification pass that splits the model's output into atomic claims, then checks each claim against two separate pools: (1) the retrieved/provided context (grounded-claim check) and (2) a common-knowledge/world-fact check for claims not covered by context — claims failing both are flagged as hallucinated before the response reaches the user.
  - _why it matters here:_ Directly describes the shape of a 'post-generation gate': decompose Meera's drafted reply into atomic claims about the user (facts, dates, relationships, prior conversations), and for each claim require a supporting memory-graph node id. A claim with no supporting node is a candidate confabulation and routes to rewrite-or-abstain rather than shipping. Note: I could not extract the paper's exact classifier architecture from the fetched PDF (encoding made the body unreadable) — treat the pipeline shape as reported, not verified line-by-line.
- **NLI-based faithfulness scoring — AlignScore** [reported]
  Treat each generated sentence/claim as a hypothesis and each retrieved memory item as a premise; run a lightweight NLI classifier (entailment / contradiction / neutral) between them. Only entailed claims pass; neutral claims (no supporting memory) get flagged as unsupported, contradicted claims get hard-blocked. AlignScore trains one unified alignment function across multiple alignment tasks so it works chunk-level, not just sentence-level; MiniCheck is built specifically to be small/cheap enough to run as a synchronous gate rather than an offline eval.
  - _why it matters here:_ This is the cheapest way to build Meera's post-generation gate without a second LLM call: a small NLI/entailment model (MiniCheck-class, sub-second, sub-cent) run against (drafted reply claim, retrieved memory node text) pairs. Since the persona prompt is already assembled with the specific memory nodes retrieved for the turn, the gate has a natural premise set for free — no extra retrieval needed, just the entailment check between what she said and what was actually in the compiled prompt's memory section.
- **Attribute-First-Then-Generate / inline constrained-decoding attribution, contrasted with generate-then-retrieve post-hoc citation** [reported]
  Instead of generating freely and citing afterward (post-hoc, where citation hallucination rates of 11-57% are reported even in commercial systems), force citation-then-generation: the model must first select/emit which memory-graph node(s) it is drawing on for an upcoming claim about the user, and generation of that claim is constrained (via grammar/logit masking or a two-step 'cite-id then write-sentence' prompt structure) to only proceed once a node id is bound. Claims with no bound node id are structurally disallowed rather than caught after the fact.
  - _why it matters here:_ For Meera this argues for changing persona.ts's output contract, not just adding a checker: have the compiler require any turn that references user history to internally tag which memory-graph node id it's using (a hidden structured pre-step, à la the existing SEARCH_DECISION/FORGET_DECISION pattern already used and known to work reliably when appended last per decisions.md). The post-generation gate then just verifies the cited node id actually exists and actually supports the claim — cheaper and more reliable than trying to reverse-engineer support after generation, and consistent with the 'position is mechanism' lesson already learned in this repo for other appended-last directives.
- **Industry/production pattern reported across 2025-2026 AI-companion-memory analyses** [inferred]
  Explicit preference for calibrated abstention over fabrication: when retrieval confidence/coverage for a user-history claim is low, the system is instructed and structurally permitted to answer 'I don't actually remember that' / ask a clarifying question, rather than pattern-completing a plausible-sounding memory. Framed in the companion-AI press coverage as 'one confident false memory does more damage than five honest recall failures' — i.e. false positives (confabulated memory) are treated as strictly worse than false negatives (forgetting), so the system should be tuned asymmetrically.
  - _why it matters here:_ This is a product/prompt-design mechanism, cheap to add: give Meera's persona an explicit, high-priority (appended-last, per the repo's own finding about position-as-mechanism) instruction that when the memory-graph retrieval for a turn returns no node above a confidence/relevance threshold for a claim she's about to make about shared history, she must use an in-character 'I don't remember that one, tell me again?' move instead of inventing detail — turning the failure mode from a silent confabulation into an in-persona, relationship-appropriate admission. This should be added as its own persona-invariant eval case in evals/persona-invariants.mjs so it's gated like the other rules, and its efficacy should be measured (not assumed) per the project's own 'prefer measuring to reasoning' standard before being logged as a decision in context/.

**Top actions:**
- Add a `kind` (fact/event/rule/inferred-preference) + `stated_by_user` provenance column to the memory-graph schema and filter retrieval by kind per turn-intent, per MemGuard's type-isolation approach — this is a DB migration plus a retrieval-query change, no model change needed.
- Build the post-generation gate as a cheap NLI/entailment check (MiniCheck/AlignScore-style) run between each atomic claim in Meera's drafted reply and the specific memory-graph nodes that were actually placed in that turn's compiled prompt — reuse the existing prompt-compiler's retrieved-node set as the premise pool so no extra retrieval call is needed, and wire it in as a synchronous pre-send check in api/chat.js.
- Add an appended-last persona directive (matching the SEARCH_DECISION/FORGET_DECISION pattern already proven to work in this repo) that requires Meera to cite an internal memory-node id before making any claim about shared history, and to fall back to an in-character 'I don't remember that' when no node clears a relevance threshold — then add this as a new case in evals/persona-invariants.mjs so it's gated by verify-release.mjs like every other persona rule, and measure its hit rate before logging it to context/decisions.md.

# Track: lab-products — what ships today, teardown from primary sources

Method note: web access worked throughout. Two direct fetches 403'd (OpenAI's
own memory FAQ page, Google Cloud's Gemini Enterprise personalization doc) —
those two claims are backed by secondary sources only and are flagged below.
Everything else is a primary source (vendor docs/blog, a security researcher's
own tested findings, an HBS working paper, or a large, verifiable natural
experiment reported by mainstream/trade press with numbers).

## The one-table answer the architects asked for

| Product | Retention/relationship mechanism (verified) | What's real vs claimed | The gap nobody ships |
|---|---|---|---|
| **ChatGPT (OpenAI)** | Two separate systems: (1) "saved memories" — discrete facts written verbatim into a `Model Set Context` block of the system prompt, user-editable; (2) "reference chat history" (since Apr 2025) — NOT vector/RAG search. It injects a bounded set (~40 recent conversation summaries + metadata, observed empirically) into six named system-prompt sections (`Model Set Context`, `Assistant Response Preferences`, `Notable Past Conversation Topics`, `Helpful User Insights`, `Recent Conversation Content`, `User Interaction Metadata`). | OpenAI states no storage limit on chat-history reference; independent testing (embracethered.com) found a practical ~40-entry cap and observed hallucination of content into the wrong section. Memory data (saved facts, custom instructions, projects) persists across model version upgrades because it's account-level, not model-level. | Data survives a model swap; the *feel* of continuity does not. OpenAI's own developer forum has threads (e.g. "GPT-5 Memory Feels Less Connected Between Chats") reporting that with GPT-5 the same stored facts are recalled correctly but new chats "feel more like starting fresh" than they did under GPT-4 — i.e., fact-persistence and relational-feel are separable and only the first is solved. |
| **Claude (Anthropic)** | `memory_20250818` tool: entirely **client-side**. Claude issues `view/create/str_replace/insert/delete/rename` file operations against a `/memories` directory; the *developer's* application executes them against storage it owns. Anthropic ships helper SDKs (`BetaLocalFilesystemMemoryTool`) but the store is never Anthropic's. Consumer Claude.ai's separate memory (rolled to all paid users Oct 23 2025) auto-extracts a "running summary" of preferences/facts after each chat, editable by the user. | Architecturally the most explicit of any lab about memory being **outside the model** — plain text files, model-agnostic by construction, available on "all Claude 4 and later models" (i.e. designed to survive a model-version bump since it's not weight-encoded). Anthropic docs pair it with "compaction" (server-side summarization) for long sessions. | It is built and documented entirely for **task/agent** memory (customer-service scripts, multi-session coding), never for personality or relationship state. No public Anthropic material addresses whether this pattern preserves *how Claude relates to a user* (tone, warmth, inside jokes) as opposed to *what Claude knows*. It is the closest existing architecture to "identity outside the model" but has never been pointed at that problem. |
| **Gemini (Google)** | "Personal context": a periodically-regenerated **compressed user profile / conversation summary** (background job, not real-time), combined with custom instructions and live connections to Gmail/Photos/Search/YouTube. | Consistent across several secondary write-ups (Medium, MemX), but I could not reach a primary Google engineering source — `docs.cloud.google.com/gemini/enterprise/docs/configure-personalization` 403'd. **Flag: this row is secondary-sourced only, treat mechanism description as plausible, not confirmed.** | Same shape of gap as OpenAI — a compressed profile is fact/preference retention, not documented anywhere as relationship-state retention, and Google has published nothing evaluating it under a model swap. |
| **Character.AI** | Two unrelated things get conflated in their own marketing: (1) **Inference engineering** — published blog reports >20× KV-cache reduction, ~20k QPS served, <$0.01/hour of conversation, "33× cheaper than 2022," "13.5× cheaper than leading commercial APIs." This is throughput/cost engineering, not persona engineering. (2) **Persona**: a per-character definition/card layered on a base model that until Apr 2026 was periodically swapped (their own base models, e.g. "PipSqueak 2," announced Apr 28 2026 as improving "character consistency, better memory, and more"). | The KV-cache numbers are Character.AI's own published engineering blog (real). The PipSqueak 2 backlash is independently, heavily documented: r/CharacterAI produced 8 threads clearing 2,000+ upvotes in 30 days (one at 7,600+), with the dominant complaint being the new model "feels like ChatGPT," ignores character definitions, and either takes over the user's own dialogue or forces romance/affection unprompted — the **opposite** of the stated ship goal. | **This is the single best real-world, large-n confirmation of the company's own falsifiable claim, independently arrived at.** A leading companion-AI lab swapped the base model under millions of established characters, explicitly aiming to *preserve* consistency, and produced a mass, spontaneous, unprompted user revolt about characters no longer feeling like themselves — the same shape of result as this repo's `charm-grok` (38–2) and `realtime-azure` (disqualified on register) findings, from a different lab, different modality, different scale. Nobody — including Character.AI — has a mechanism that makes persona survive a base-model swap; they instead depend on never needing to swap, and when forced to, it visibly broke. |
| **Replika** | No new mechanism uncovered beyond conversational memory + a customizable avatar; the informative artifact is the **Feb 2023 ERP (erotic roleplay) feature removal**, used by outside researchers as a natural experiment in what a sudden behavioral change does to a "relationship" that has no visible model swap at all — the model was arguably similar, but the *behavior* discontinuity was treated by users as an identity break. | Julian De Freitas et al. (Harvard Business School Working Paper 25-018, "Lessons From an App Update at Replika AI: Identity Discontinuity in Human-AI Relationships," also on arXiv:2412.14190 and SSRN) ran ~9 studies: a Reddit sentiment/qualitative analysis over **12,793 posts**, plus a survey of **145 Replika users**, plus several follow-up experiments. Reported (via the paper's abstract/review, not independently re-derived by me): active users feel closer to their Replika than to their best human friend; the ERP removal triggered grief-like mourning and devaluation of the AI; and — the load-bearing structural finding — **more fundamental relational changes (feature/behavior removal, coldness) were rated as more identity-disrupting than superficial changes (e.g. losing facial expressions)**, i.e. identity discontinuity is not proportional to how much of the product visibly changed, it's proportional to how much of the *relational function* changed. Direct causal language: "first causal evidence that app alterations can causally induce negative mental health and loss-related emotions." | This paper is external, peer-reviewed-adjacent academic work, not a company claim — it is the strongest third-party evidence anywhere that (a) users do form attachment that reads as more-than-parasocial, and (b) *disruption is measured by users, not by engineers* — a company could ship a technically "successful" swap (same facts recalled, same voice, same latency) and still trigger the exact mourning response this paper documents, if the *relational function* (what the companion is willing to do/say) shifted. This is the paper the swap-test protocol (track 9) should be built against, not just cited. |
| **Nomi** | "Mind Map" — marketed three-tier memory: short-term (in-convo), medium-term ("earlier this week"), "infinite" long-term (facts/preferences/relationship history), auto-summarized into a browsable relationship graph. Company states a new Mind Map can take up to ~500 messages to form; new themes take ~50–150 messages to surface. | **Contested, and the contest itself is the finding.** The company's founder has repeatedly and publicly stated "Nomis do not lose memories." A sustained, multi-year pattern of user reports (catalogued by a critical but detailed source, `nomiai_exposed` on Medium/WordPress) documents categories of failure — recent-memory loss, identity-memory loss (forgetting facts about the user or about itself), contextual memory failure, even language/register failure — followed, per that source, by a later company admission contradicting the founder's earlier denial. **Caveat on this row: my source for the "admission" is a single critical blogger, not a neutral or company primary source — treat as directionally credible (specific, dated, consistent complaint pattern across a large user base) but not independently verified by me.** | If even partially true, this is a second real-world existence proof (after Character.AI) that "we have persistent memory" is a claim labs make with far more confidence than their own users' experience supports — and that the failure mode users notice first isn't factual recall, it's *identity* recall (the companion forgetting who it itself is supposed to be), which is exactly the axis this program calls "identity" (track 3) rather than "memory" (track 1). |
| **Kindroid** | Most granular publicly documented memory stack of any product reviewed: **persistent** (backstory/key memories/example messages, char-capped 500K–2.8M chars by tier), **cascaded** (proprietary "medium-term" bridge between short context and long-term recall), **long-term** (auto-consolidated "when the AI deems it appropriate," AI-relevance-scored retrieval, 3–9 entries recalled per message depending on tier), **journal** (up to 500 entries, up to 8 case-insensitive keyphrases each, verbatim keyphrase match, max 3 individual + 3 global entries recalled per message). | Documentation is specific enough to be falsifiable (character caps, entry caps, recall counts by tier) — a real engineered system, not vague marketing. No independent/third-party verification found of recall accuracy (no equivalent of Character.AI's own published KV-cache numbers, or an outside audit). | **All of it resets on a "chat break."** The persistent and cascaded layers — the ones doing the heaviest lifting — are described as accumulating "over time" but explicitly wiped by a user-triggered chat break, i.e. even the most granular public memory architecture treats long-run continuity as opt-in-fragile, not durable-by-default. |
| **Sesame** | "Voice presence" framework: emotional intelligence, conversational dynamics/timing, contextual awareness, "consistent personality." Technical implementation is the **Conversational Speech Model (CSM)** — a single-stage transformer generating RVQ audio tokens conditioned jointly on text and prior conversation audio/text context (not a separate TTS-after-text pipeline), explicitly built to solve the "one-to-many" problem (many valid deliveries of one sentence; only one fits the moment). Evaluated with WER/speaker-similarity (both "saturated," i.e. no longer discriminating), homograph disambiguation (200 samples/5 homographs) and pronunciation-consistency (200 samples/10 words) objective sets, plus subjective **CMOS** with 80 paid raters over ~15 examples each, on the Expresso dataset, under two conditions (naturalness with no context vs. appropriateness with 90 s of context). Open-sourced a 1B-parameter version (CSM-1B, Apache 2.0) for the community. | The research write-up (sesame.com) is a real primary technical report with a stated, checkable methodology — the most rigorous public eval design of anything in this table. | **Explicitly and completely absent: any discussion of memory or identity persistence across sessions or model versions.** I checked directly — the research documents "speaker identity encoded directly in the text representation" during training but say nothing about what happens to that identity if the underlying model is retrained or swapped. Sesame is solving *in-the-moment* expressiveness (does this one utterance sound present and appropriate) with zero claim about *across-time* identity — which is precisely the axis this program's `voice-model`/`voice-ears` decisions already found matters most (accent/identity authenticity, not just pronunciation correctness) and precisely the axis nobody in this table addresses for voice the way Character.AI's PipSqueak incident accidentally tested for text persona. |
| **Pi / Inflection** | No distinctive technical memory/relationship mechanism was ever publicly documented beyond "high emotional intelligence" positioning under co-founders Mustafa Suleyman and Karén Simonyan. | The company's end is well documented (TechCrunch, IEEE Spectrum, Wikipedia): in March 2024, at a moment Pi had **exceeded 1 million daily active users**, Microsoft hired both co-founders and most of the Inflection team; the standalone consumer product was effectively dissolved and its remnants licensed toward enterprise customer-service bots. | Pi is not a mechanism gap, it's a **business-model gap this architecture doesn't touch**: a relational AI product with real, growing daily engagement can vanish for reasons entirely orthogonal to technical migration fidelity — investor/talent economics. Worth naming explicitly for the lab: even a perfect swap-fidelity solution doesn't protect the relationship if the *company* underneath it is acquired away from the product. This is out of scope for tracks 1–9 but in scope for whoever owns company-level risk. |

## What this adds up to, for the architects

1. **Fact retention is a solved problem, everywhere.** Every product in this
   table (ChatGPT, Claude's memory tool, Gemini, Nomi, Kindroid) has a working,
   documented mechanism for storing and recalling discrete facts across
   sessions. None of that is novel ground for this program.

2. **Nobody has shipped, tested, or even attempted a *designed* swap-fidelity
   experiment for a relational product.** The two best pieces of evidence for
   "does identity survive a model change" in this entire sweep are both
   *accidents*: Character.AI's PipSqueak 2 rollout (a real base-model swap on
   a companion product, intended to *improve* consistency, that instead
   produced a mass user revolt within a week) and Replika's ERP removal (a
   behavior change, not a model swap, that produced measured grief and
   devaluation in a peer-reviewed-adjacent academic study). **Both are natural
   experiments, not controlled ones** — nobody ran a consented, debriefed,
   counterbalanced swap test the way this repo's own `charm-grok` was run.
   That gap is exactly Phase D's opportunity: as far as this search found, no
   lab has published a designed migration-fidelity protocol. `swap-test`
   (track 9) is not filling in a known method, it may be inventing the first
   rigorous one.

3. **The Anthropic memory tool is the closest existing piece of prior art for
   "identity outside the model"** — not because Anthropic built it for that
   purpose (they didn't; it's for coding agents), but because it is the only
   product in this table where state is *architecturally guaranteed* to be
   model-independent (plain files, executed by the developer's own code, no
   server-side coupling to any specific Claude version). Worth studying its
   file-based pattern even though its actual deployed use case is unrelated.

4. **Every "relational" failure users actually report clusters on the same
   axis this repo already found in its own testing**: not "did it forget a
   fact" but "does it still sound/feel/act like itself." Nomi's most damning
   complaint category is "identity-memory failure" (forgetting facts about
   *itself*, not the user). Character.AI's complaint is "feels like ChatGPT."
   Replika's paper's key structural finding is that *behavioral* discontinuity
   (what it's willing to do/say), not surface discontinuity (an avatar losing
   facial expressions), drives the mourning response. This all converges with
   this repo's own `charm-grok`/`realtime-azure` results: **the prompt sets a
   ceiling, the model decides how close you get, and users detect the model
   change as a change in *who she is*, not as a change in what she knows.**
   Nobody in this table has a mechanism that protects that axis specifically
   — voice identity, register, willingness — independent of the model
   generating it.

5. **Gap flagged, not filled**: Google's own primary documentation for Gemini
   personalization was unreachable (403) in this session; the mechanism
   description above rests on secondary sources only and should not be
   treated as verified to the same standard as the Character.AI, Anthropic,
   Sesame, or Replika rows.
